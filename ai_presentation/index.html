01 · Models — not all are equal cost vs. brains

⚡ Small & cheap

GPT-6 Luna, Claude Haiku 5.5

  • Fast, ~$0.10 / $0.50 per 1M tokens (in/out)
  • Great for: autocomplete, renames, boilerplate, simple tests, summaries, commit messages
  • Struggles with: multi-file refactors, subtle bugs, architecture

🧠 Frontier & pricier

GPT-6.1 Sol, Claude Opus 5.5

  • $2–$4 in / $10–$20 out per 1M tokens
  • Great for: agent mode, debugging, design, large refactors, code review
  • Overkill for: one-line edits and trivial questions

Rule of thumb: start cheap for simple tasks, switch up the moment the model goes in circles. A retry loop on a weak model usually costs more than one shot with a strong one.

02 · Effort — how hard should it think?

Reasoning models "think" before answering. Effort sets the thinking budget.

low
medium
high
xhigh
max

more thinking → better on hard problems, but slower & more tokens

Low

Quick edits, lookups, formatting. Near-instant, cheap.

Medium / High

Default for most coding work. Good balance.

XHigh / Max

Gnarly bugs, algorithms, big plans. Can take minutes and many tokens.

Model and effort are two separate knobs. A small model at max effort is still a small model — and a frontier model at low effort is often enough.

03 · Permissions — what may the agent do alone?

✅ Allow

Runs without asking. Safe, read-only or reversible: git status, npm test, reading files.

❓ Ask

Pauses for your approval. File edits, installing packages, network calls.

⛔ Deny

Never allowed. rm -rf, git push --force, reading .env / secrets.

// e.g. Claude Code .claude/settings.json — Copilot has equivalent tool-approval settings
{
  "permissions": {
    "allow": ["Bash(npm test:*)", "Bash(git status)"],
    "deny":  ["Bash(git push --force:*)", "Read(./.env)"]
  }
}

Goal: fewer interruptions for safe stuff, a hard stop for dangerous stuff. Never "allow everything" on a machine with prod credentials.

Hooks — your scripts, run automatically

Hooks are shell commands that fire on agent lifecycle events. Deterministic — they always run, unlike instructions the model might ignore.

Before a tool runs

Block dangerous commands, protect files, validate inputs.

After a tool runs

Auto-format, lint, run tests on edited files.

Session start / stop

Load context, send a notification, log usage.

# "after every file edit, run prettier on it"
{ "hooks": { "PostToolUse": [ { "matcher": "Edit|Write",
    "hooks": [ { "type": "command", "command": "npx prettier --write \"$FILE\"" } ] } ] } }

Instructions = suggestions. Hooks = guarantees.

04 · MD files — the project's memory

Markdown files the agent reads automatically at the start of every chat. Write once, stop repeating yourself.

.github/copilot-instructions.md

Repo-wide rules for Copilot: stack, conventions, how to build & test.

AGENTS.md / CLAUDE.md

Same idea, open standard read by most agents (Copilot, Claude, Codex…). Can be nested per folder.

*.instructions.md

Scoped rules via applyTo: "**/*.ts" — only loaded for matching files.

## Build & test
- Run `npm run test:unit` before finishing any task
## Conventions
- Use our `ApiClient` wrapper, never raw fetch
- No new dependencies without asking

Keep it short & concrete. Every line costs context on every request.

Agents — specialised AI teammates

An agent = a model + its own instructions + a limited set of tools, working in a loop until the task is done.

  • Agent mode in Copilot Chat — edits files, runs commands, iterates
  • Copilot coding agent — assign an issue, get a PR back
  • Custom agents — e.g. "reviewer", "test-writer", "docs" with focused prompts
  • Sub-agents — the main agent delegates research to a helper with fresh context
# .github/agents/reviewer.agent.md
---
name: reviewer
description: Reviews diffs for bugs
  and security issues
tools: ['read', 'search']
model: Claude Opus 5.5
---
You are a strict code reviewer.
Report only real bugs, one per line,
with file:line and a suggested fix.

Skills — reusable know-how, loaded on demand

A skill is a folder with a SKILL.md (+ optional scripts/templates). Only the short description is always in context; the full content loads when the task matches.

  • "How we write DB migrations"
  • "Release checklist"
  • "Generate a PDF report with our template"

MD files = always on. Skills = pulled in only when relevant → saves context.

# .github/skills/db-migration/SKILL.md
---
name: db-migration
description: Use when creating or
  changing database migrations.
---
1. Run `npm run migrate:new <name>`
2. Always write the `down` step
3. Test on a copy of staging data
4. Never edit a merged migration
