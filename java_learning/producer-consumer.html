4. Producer-consumer & the concurrency utilities

The most common concurrency pattern, built four ways (from wait/notify to virtual threads), then a tour of java.util.concurrent: queues, Semaphore, CountDownLatch, CyclicBarrier, Phaser, Exchanger, concurrent collections, ForkJoin.

The pattern

Producers create work, consumers process it, a buffer between them decouples their speeds. The buffer must be thread-safe and should be bounded: an unbounded buffer just moves the problem to an OutOfMemoryError. A full bounded buffer makes producers wait: that is backpressure.

You meet this pattern everywhere: a thread pool (submitters → work queue → workers), Tomcat (acceptor → queue → worker threads), logging appenders (async appender), RabbitMQ (publishers → queue → consumers), Reactor (Flux with request(n)).

Version 1: wait / notify (how it works underneath)

class BoundedBuffer<T> {
    private final Deque<T> items = new ArrayDeque<>();
    private final int capacity;
    BoundedBuffer(int capacity) { this.capacity = capacity; }

    public synchronized void put(T item) throws InterruptedException {
        while (items.size() == capacity) {   // WHILE, not if: re-check after waking (spurious wakeups, other producers)
            wait();                          // releases the monitor and sleeps
        }
        items.addLast(item);
        notifyAll();                         // wake consumers (notify() could wake another producer and stall)
    }

    public synchronized T take() throws InterruptedException {
        while (items.isEmpty()) {
            wait();
        }
        T item = items.removeFirst();
        notifyAll();                         // wake producers waiting for space
        return item;
    }
}
The rules of wait/notify
  • You must hold the object's monitor (synchronized) to call wait/notify, else IllegalMonitorStateException.
  • Always wait in a while loop that re-checks the condition.
  • Prefer notifyAll() when producers and consumers wait on the same monitor.
  • In real code, don't write this: use a BlockingQueue.

Version 2: ReentrantLock + two Conditions

Separate wait sets for "not full" and "not empty" mean we wake only the right kind of thread. This is essentially how ArrayBlockingQueue is implemented.

class BoundedBuffer2<T> {
    private final Object[] items;
    private int putIdx, takeIdx, count;
    private final ReentrantLock lock = new ReentrantLock();
    private final Condition notFull = lock.newCondition();
    private final Condition notEmpty = lock.newCondition();

    BoundedBuffer2(int capacity) { items = new Object[capacity]; }

    public void put(T x) throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == items.length) notFull.await();
            items[putIdx] = x;
            putIdx = (putIdx + 1) % items.length;       // circular array
            count++;
            notEmpty.signal();                          // wake ONE consumer
        } finally { lock.unlock(); }
    }

    @SuppressWarnings("unchecked")
    public T take() throws InterruptedException {
        lock.lockInterruptibly();
        try {
            while (count == 0) notEmpty.await();
            T x = (T) items[takeIdx];
            items[takeIdx] = null;
            takeIdx = (takeIdx + 1) % items.length;
            count--;
            notFull.signal();                           // wake ONE producer
            return x;
        } finally { lock.unlock(); }
    }
}

Version 3: BlockingQueue (the right way)

record Job(long id, String payload) {}
static final Job POISON = new Job(-1, "");                       // "poison pill": tells a consumer to stop

BlockingQueue<Job> queue = new ArrayBlockingQueue<>(1_000);

Runnable producer = () -> {
    try {
        for (long i = 0; i < 10_000; i++) queue.put(new Job(i, "data-" + i));   // blocks while full
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};

Runnable consumer = () -> {
    try {
        while (true) {
            Job job = queue.take();                              // blocks while empty
            if (job == POISON) return;
            process(job);
        }
    } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
};

try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    int consumers = 4;
    for (int i = 0; i < consumers; i++) exec.submit(consumer);
    exec.submit(() -> { producer.run(); for (int i = 0; i < consumers; i++) queue.put(POISON); return null; });
}   // close() waits for everybody

Stopping consumers cleanly

Poison pill

Put one special element per consumer after the last real item. Consumers finish everything queued before stopping. Simple, but you must know the consumer count.

Interrupt / shutdownNow

executor.shutdownNow() interrupts the consumers; take() throws InterruptedException. Fast, but items still in the queue are not processed (shutdownNow returns only the executor's never-started tasks, not the items left in your BlockingQueue).

Producer-consumer in Spring Boot

In-process: an audit-event writer that batches inserts

Request threads produce audit events; one background consumer drains the queue and writes them in batches. SmartLifecycle lets Spring start it after the context is ready and stop it (flushing the queue) on shutdown.

flowchart LR
  R1[request thread] -- offer --> Q[(ArrayBlockingQueue 10 000)]
  R2[request thread] -- offer --> Q
  R3[request thread] -- offer --> Q
  Q -- "poll + drainTo(500)" --> W[audit-writer thread]
  W -- batch INSERT --> DB[(DB)]

@Component
public class AuditWriter implements SmartLifecycle {
    private static final Logger log = LoggerFactory.getLogger(AuditWriter.class);
    private final BlockingQueue<AuditEvent> queue = new ArrayBlockingQueue<>(10_000);
    private final JdbcTemplate jdbc;
    private volatile boolean running;
    private Thread worker;

    public AuditWriter(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    /** Producer side: called from request threads. Never blocks the request. */
    public void record(AuditEvent e) {
        if (!queue.offer(e)) log.warn("audit queue full, dropping {}", e);   // or: metrics + fallback
    }

    @Override public void start() {
        running = true;
        worker = Thread.ofPlatform().name("audit-writer").start(this::consume);
    }

    private void consume() {
        List<AuditEvent> batch = new ArrayList<>(500);
        while (running || !queue.isEmpty()) {
            try {
                AuditEvent first = queue.poll(1, TimeUnit.SECONDS);    // wait at most 1 s
                if (first == null) continue;
                batch.add(first);
                queue.drainTo(batch, 499);                             // grab up to 499 more without waiting
                jdbc.batchUpdate("insert into audit(at, who, what) values (?,?,?)", batch, batch.size(),
                        (ps, ev) -> { ps.setObject(1, ev.at()); ps.setString(2, ev.who()); ps.setString(3, ev.what()); });
            } catch (InterruptedException ie) {
                Thread.currentThread().interrupt();
                return;
            } catch (Exception ex) {
                log.error("audit batch failed", ex);
            } finally {
                batch.clear();
            }
        }
    }

    @Override public void stop() {
        running = false;                       // consumer drains what is left, then exits
        try { worker.join(5_000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
    @Override public boolean isRunning() { return running; }
}
The limit of in-process queues If the pod crashes, everything in memory is lost, and each instance has its own queue. When the work must survive restarts or be shared by several instances, put a message broker in the middle: RabbitMQ (Q56–65) or Kafka. The pattern is the same, the buffer just lives outside your JVM.

Semaphore: limit how many at once

A counter of permits. acquire() takes one (waits if none), release() gives one back. Use it to cap concurrent access to something, e.g. a partner API that allows 10 parallel calls. Especially important with virtual threads, where there is no pool size to limit you.

flowchart LR
  T1[thread] --> S{{Semaphore permits=3}}
  T2[thread] --> S
  T3[thread] --> S
  T4[thread waits] -.-> S
  S --> API[partner API: max 3 concurrent]

private final Semaphore permits = new Semaphore(10, true);   // fair

public Quote quote(Request r) throws InterruptedException {
    if (!permits.tryAcquire(200, TimeUnit.MILLISECONDS)) throw new TooBusyException();  // → HTTP 429/503
    try { return partner.quote(r); }
    finally { permits.release(); }
}

A semaphore with 1 permit acts like a lock, but any thread may release it (no ownership).

CountDownLatch: wait until N things happened

A one-shot gate: initialized with a count; threads call countDown(); await() blocks until the count reaches zero. Cannot be reset.

sequenceDiagram
  participant M as main thread
  participant A as cache warm-up
  participant B as connect broker
  participant C as load config
  M->>M: latch = new CountDownLatch(3)
  M->>M: await()
  A-->>M: countDown() → 2
  C-->>M: countDown() → 1
  B-->>M: countDown() → 0
  M->>M: continues

CountDownLatch ready = new CountDownLatch(3);
for (Runnable init : List.<Runnable>of(this::warmCache, this::connectBroker, this::loadConfig)) {
    Thread.startVirtualThread(() -> { try { init.run(); } finally { ready.countDown(); } });
}
if (!ready.await(30, TimeUnit.SECONDS)) throw new IllegalStateException("startup timed out");

// Classic test trick: release many threads at the same instant to provoke races
CountDownLatch startGun = new CountDownLatch(1);
for (int i = 0; i < 100; i++) exec.submit(() -> { startGun.await(); service.reserve("sku", 1); return null; });
startGun.countDown();

CyclicBarrier: N threads meet, then all continue

N threads each call await(); all wait until the N-th arrives, an optional barrier action runs, then all continue. Reusable for the next round (hence "cyclic").

int workers = 4;
CyclicBarrier barrier = new CyclicBarrier(workers, () -> log.info("all parts done, merging round"));
for (int w = 0; w < workers; w++) {
    int part = w;
    exec.submit(() -> {
        for (int round = 0; round < 10; round++) {
            simulatePart(part, round);
            barrier.await();                // everyone waits for the slowest each round
        }
        return null;
    });
}

Phaser and Exchanger

// Phaser: like a CyclicBarrier whose number of parties can change between phases
Phaser phaser = new Phaser(1);                     // the coordinator itself is registered
for (Task t : tasks) {
    phaser.register();
    exec.submit(() -> {
        t.stepOne();  phaser.arriveAndAwaitAdvance();   // phase 0
        t.stepTwo();  phaser.arriveAndDeregister();     // phase 1, then leave
        return null;
    });
}
phaser.arriveAndAwaitAdvance();                    // coordinator waits for phase 0
phaser.arriveAndDeregister();

// Exchanger: two threads swap objects at a meeting point (e.g. swap a full buffer for an empty one)

if (!map.containsKey(k)) map.put(k, load(k));
// RIGHT
map.computeIfAbsent(k, this::load);   // keep the function short: it runs while holding the bin's lock

ForkJoinPool and work stealing

For CPU-bound divide and conquer: split a big task into subtasks until small, compute, join results. Each worker has its own deque; idle workers steal tasks from the tail of busy workers' deques, keeping all cores busy.

flowchart TB
  T["sum(0..1 000 000)"] --> A["sum(0..500 000)"]
  T --> B["sum(500 000..1 000 000)"]
  A --> A1["sum(0..250 000)"]
  A --> A2["sum(250 000..500 000)"]
  B --> B1["..."]
  B --> B2["..."]

class SumTask extends RecursiveTask<Long> {
    private final long[] a; private final int lo, hi;
    SumTask(long[] a, int lo, int hi) { this.a = a; this.lo = lo; this.hi = hi; }
    protected Long compute() {
        if (hi - lo <= 10_000) {                     // small enough: do it directly
            long s = 0; for (int i = lo; i < hi; i++) s += a[i]; return s;
        }
        int mid = (lo + hi) >>> 1;
        SumTask left = new SumTask(a, lo, mid);
        left.fork();                                  // push to my deque (others may steal it)
        long right = new SumTask(a, mid, hi).compute();   // do the other half myself
        return right + left.join();
    }
}
long total = ForkJoinPool.commonPool().invoke(new SumTask(data, 0, data.length));
// Parallel streams use the same common pool under the hood:
long total2 = Arrays.stream(data).parallel().sum();
Never do blocking I/O in the common pool or in parallel streams inside a web app: the pool is shared by the whole JVM and has only cores − 1 threads.
