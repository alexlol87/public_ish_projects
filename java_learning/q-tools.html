Maven

Q81.Explain the Maven build lifecycle.

Maven has three built-in lifecycles: clean (delete target/), default (build and ship), site (project documentation). A lifecycle is an ordered list of phases; running a phase runs all phases before it. The work itself is done by plugin goals bound to phases.

flowchart LR
  V[validate] --> C[compile] --> T[test] --> P[package] --> IT[integration-test] --> VE[verify] --> I[install] --> D[deploy]
PhaseWhat happens (default bindings for a JAR)
validatecheck the POM is correct
compileresources:resources copies resources, compiler:compile compiles src/main/java
testcompiler:testCompile then surefire:test runs unit tests (*Test.java)
packagejar:jar builds target/app-1.0.jar (Spring Boot plugin repackages it into an executable fat JAR)
integration-test / verifyfailsafe runs *IT.java; verify checks results, coverage (JaCoCo), quality rules
installcopy the artifact to your local repository ~/.m2/repository (so other local projects can use it)
deployupload to the remote repository (Nexus/Artifactory) for others and for deployment

(The full default lifecycle has more phases, e.g. generate-sources, process-resources, test-compile, pre-integration-test.)

mvn clean verify                    # the typical CI command: clean, then everything up to verify
mvn clean install -DskipTests       # build and install locally, skip running tests
mvn -pl orders-service -am package  # only one module (+ the modules it depends on)
mvn dependency:tree                 # run a single plugin goal directly
mvn spring-boot:run                 # goal from the Spring Boot plugin
Q82.How do you manage dependencies and resolve conflicts in Maven?

You declare direct dependencies by coordinates (groupId:artifactId:version) and a scope; Maven downloads them and their transitive dependencies from repositories (Maven Central, your Nexus).

How Maven picks a version when two paths disagree ("dependency mediation")

flowchart TB
  APP[my-app] --> A[lib-a 1.0] --> J1[jackson-databind 2.15]
  APP --> B[lib-b 1.0] --> C[lib-c 1.0] --> J2[jackson-databind 2.17]
  N["Nearest wins: 2.15 (depth 2) beats 2.17 (depth 3)
same depth → first declared in the POM wins
NOT the newest!"]

This can silently pick an old version and cause NoSuchMethodError/ClassNotFoundException at runtime. Tools to control it:

<!-- 1. dependencyManagement: pin versions centrally (also for transitive deps); Spring Boot's parent does this for ~hundreds of libs -->
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>com.fasterxml.jackson</groupId>
      <artifactId>jackson-bom</artifactId>
      <version>2.17.2</version>
      <type>pom</type>
      <scope>import</scope>              <!-- import a BOM -->
    </dependency>
  </dependencies>
</dependencyManagement>

<!-- 2. exclusions: cut an unwanted transitive dependency -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-web</artifactId>
  <exclusions>
    <exclusion>
      <groupId>org.springframework.boot</groupId>
      <artifactId>spring-boot-starter-tomcat</artifactId>   <!-- e.g. to use Jetty instead -->
    </exclusion>
  </exclusions>
</dependency>
mvn dependency:tree -Dverbose -Dincludes=com.fasterxml.jackson.core   # who brings which version, and what was omitted
mvn dependency:analyze                                                # used-but-undeclared / declared-but-unused
mvn versions:display-dependency-updates                               # what can be upgraded
  • Maven Enforcer plugin rules (dependencyConvergence, requireUpperBoundDeps, banDuplicatePomDependencyVersions) fail the build on conflicts instead of discovering them in production.
  • With Spring Boot, don't set versions for libraries Boot manages; override via properties (<jackson-bom.version>) only when needed.
  • Security: OWASP Dependency-Check / Dependabot / Snyk scan for vulnerable versions.
Q83.SNAPSHOT vs release versions, and multi-module projects?

SNAPSHOT: 1.4.0-SNAPSHOT

"Work in progress towards 1.4.0". Can be redeployed many times; the repository stores timestamped builds (1.4.0-20261123.101500-7) and Maven re-checks for newer ones (daily by default, -U forces). Used between developers/CI during development. Never depend on snapshots in a release.

Release: 1.4.0

Immutable: once deployed to the release repository it never changes (Nexus forbids redeploy). Reproducible builds and safe deployments. Created by the Maven Release plugin (release:prepare / release:perform: removes -SNAPSHOT, tags Git, bumps to 1.4.1-SNAPSHOT) or by CI setting ${revision}.

Multi-module projects

flowchart TB
  P["trading-platform (parent POM, packaging pom)
dependencyManagement, pluginManagement, modules"]
  P --> API[trading-api: DTOs, contracts]
  P --> CORE[trading-core: domain logic]
  P --> SVC[trading-service: Spring Boot app]
  SVC --> CORE --> API

<!-- parent pom.xml -->
<groupId>com.acme.trading</groupId>
<artifactId>trading-platform</artifactId>
<version>${revision}</version>
<packaging>pom</packaging>
<properties><revision>1.4.0-SNAPSHOT</revision></properties>   <!-- CI-friendly: mvn -Drevision=1.4.0 deploy -->
<modules>
  <module>trading-api</module>
  <module>trading-core</module>
  <module>trading-service</module>
</modules>
  • Aggregation (<modules>): one command builds all modules; the reactor sorts them by inter-module dependencies.
  • Inheritance (<parent>): children inherit properties, dependencyManagement, pluginManagement. Often the same POM does both.
  • Build parts: mvn -pl trading-service -am install (-am = also make its dependencies), -amd = also modules that depend on it. Parallel: mvn -T 1C.
  • All modules usually share one version and are released together. (When using ${revision}, add the flatten-maven-plugin so deployed POMs contain the real version.)

Jenkins & CI/CD

Q84.What is Jenkins, and how does a Jenkins pipeline work?

Jenkins is an open-source automation server for CI/CD. A controller (formerly "master") schedules jobs and serves the UI; agents (nodes, often Docker/Kubernetes pods) run the builds. Hundreds of plugins integrate Git, Maven, Sonar, Docker, Slack, credentials stores.

A pipeline is defined as code in a Jenkinsfile in the repo (Groovy-based DSL). A Multibranch Pipeline job discovers branches/PRs and runs each one's Jenkinsfile, triggered by webhooks.

flowchart LR
  GH[Git push / PR] -->|webhook| C[Jenkins controller]
  C -->|schedules| A1[agent: maven + jdk25 pod]
  A1 --> S1[Checkout] --> S2[Build & unit test] --> S3[Sonar + quality gate] --> S4[Publish artifact] --> S5[Deploy DEV]
  S5 --> S6{Manual approval?} --> S7[Deploy PROD]
  C --> UI[UI: stages, logs, test reports]

// Jenkinsfile (declarative pipeline)
pipeline {
    agent { label 'maven-jdk25' }
    options { timeout(time: 30, unit: 'MINUTES'); buildDiscarder(logRotator(numToKeepStr: '20')) }
    environment { NEXUS = credentials('nexus-deploy') }     // injects NEXUS_USR / NEXUS_PSW, masked in logs
    stages {
        stage('Build & test') {
            steps { sh 'mvn -B clean verify' }
            post { always { junit '**/target/surefire-reports/*.xml' } }
        }
        stage('Sonar') {
            steps {
                withSonarQubeEnv('sonar') { sh 'mvn -B sonar:sonar' }
                timeout(time: 5, unit: 'MINUTES') { waitForQualityGate abortPipeline: true }
            }
        }
        stage('Publish') {
            when { branch 'main' }
            steps { sh 'mvn -B deploy -DskipTests -Drevision=1.4.${BUILD_NUMBER}' }
        }
        stage('Deploy to TEST') {
            when { branch 'main' }
            steps { sh './deploy.sh test 1.4.${BUILD_NUMBER}' }     // e.g. triggers DeployIT
        }
        stage('Deploy to PROD') {
            when { branch 'main' }
            input { message 'Deploy to production?' }               // manual approval gate
            steps { sh './deploy.sh prod 1.4.${BUILD_NUMBER}' }
        }
    }
    post {
        failure { slackSend channel: '#team', message: "Build failed: ${env.BUILD_URL}" }
    }
}
  • Declarative (above, structured, recommended) vs scripted (node { … }, plain Groovy, more flexible).
  • Shared libraries: reusable pipeline steps across many repos (@Library('ci-lib') _).
  • parallel { } runs stages concurrently; stash/unstash passes files between agents.
Q85.Describe a good CI/CD pipeline for a Java microservice.
flowchart TB
  subgraph CI["Continuous Integration: every push or PR, fast feedback under 10 min"]
    A[Checkout] --> B[Compile + unit tests + JaCoCo coverage]
    B --> C[Static analysis: SonarQube quality gate, Checkstyle/SpotBugs]
    C --> D[Integration tests: Testcontainers DB, RabbitMQ; contract tests]
    D --> E[Security: dependency CVE scan, secret scan]
    E --> F[Build ONE immutable artifact: JAR + Docker image tagged with version / commit]
    F --> G[Publish: Nexus / container registry, image scan]
  end
  subgraph CD["Continuous Delivery: promote the SAME artifact"]
    G --> H[Deploy DEV automatically + smoke tests]
    H --> I[Deploy TEST/UAT: DB migrations Flyway/Liquibase, e2e and performance tests]
    I --> J{Approval / change ticket}
    J --> K[Deploy PROD: blue-green or canary, health checks]
    K --> L[Monitor: error rate, latency; automatic rollback]
  end

Principles that make it "good":

  • Build once, deploy many: the exact artifact tested in TEST goes to PROD; only configuration differs (Q38).
  • Fast feedback: unit tests and static checks first; fail fast; PR builds must pass before merge (branch protection).
  • Everything as code: Jenkinsfile, Dockerfile, Helm charts/K8s manifests, DB migrations versioned in Git.
  • Quality gates: coverage on new code, no new critical issues, no high CVEs.
  • Safe database changes: backward-compatible migrations (expand/contract) so old and new versions run side by side during rollout.
  • Progressive delivery: rolling/blue-green/canary, readiness probes, feature flags to decouple deploy from release.
  • Rollback is one click (redeploy previous version), and tested.
  • Traceability: version ↔ commit ↔ ticket ↔ deployment record (audit for regulated environments).
  • Secrets from a vault, never in the repo or the image.

Merge vs rebase

Golden rule of rebasing Never rebase commits that others have already pulled (e.g. main). Rebase your own feature branch onto main to update it (git pull --rebase, git rebase origin/main), then push with git push --force-with-lease (refuses if someone else pushed meanwhile).
git switch -c feature/ABC-123 origin/main
# … commits …
git fetch origin
git rebase origin/main          # replay my commits on the latest main
git rebase -i origin/main       # optionally squash/reword commits before review
git push --force-with-lease
# PR → review → "Squash and merge" or "Rebase and merge"

Quality, support, deployment

Q88.What is SonarQube, and what does it check?

SonarQube is a static code analysis platform: it scans source code (without running it) on every build, stores results over time, and decides via a quality gate whether the code is acceptable. SonarQube Cloud (formerly SonarCloud) is the hosted version; SonarQube for IDE (formerly SonarLint) shows the same issues in your editor.

What it reportsExamples
Bugs (reliability)possible NullPointerException, resource not closed, equals without hashCode, wrong BigDecimal comparison
Vulnerabilities (security)SQL injection via string concatenation, weak crypto, hard-coded credentials, path traversal
Security hotspotssecurity-sensitive code a human must review (CORS config, regex DoS, disabled CSRF)
Code smells (maintainability)high cognitive complexity, long methods, unused code, duplicated blocks, naming
Coverage% of lines/branches covered by tests (imported from JaCoCo reports; Sonar doesn't run tests)
Duplications% duplicated lines
Technical debtestimated time to fix all code smells; A–E ratings

Newer versions classify issues by software quality (Security, Reliability, Maintainability) and severity, but the ideas are the same.

  • Quality profile: which rules are active per language (e.g. "Sonar way").
  • Quality gate: pass/fail conditions, by default focused on new code ("clean as you code"): e.g. coverage on new code ≥ 80 %, no new bugs/vulnerabilities, all new hotspots reviewed, duplication ≤ 3 %. The pipeline fails if the gate fails (waitForQualityGate in Jenkins, Q84).
  • PR decoration: issues shown as comments on the pull request.
mvn clean verify sonar:sonar -Dsonar.host.url=https://sonar.acme.com -Dsonar.token=$SONAR_TOKEN

The repository's own springboot_java_utilities project shows SonarQube next to Checkstyle, SpotBugs and PMD on a demo Spring Boot app.

Q89.What is Kibana, and how would you use it for support?

Kibana is the web UI of the Elastic Stack: it queries and visualizes data stored in Elasticsearch. In the ELK stack, applications' logs are collected (Filebeat / Elastic Agent), optionally parsed and enriched (Logstash or ingest pipelines), stored in Elasticsearch, and explored in Kibana.

flowchart LR
  A1[orders pods: JSON logs to stdout] --> FB[Filebeat / Elastic Agent]
  A2[pricing pods] --> FB
  FB --> LS[Logstash: parse, enrich, mask PII]
  LS --> ES[(Elasticsearch: logs-* data streams)]
  ES --> K[Kibana: Discover, Dashboards, Alerts]

A support investigation, step by step

  1. Ticket: "Client X got an error placing an RFQ around 14:05". Open Discover, set the time range 13:55–14:15.
  2. Filter with KQL (Kibana Query Language): 
    service.name : "rfq-service" and log.level : "ERROR" and client.id : "X"
  3. Find the error, copy its trace.id, then search all services by it: trace.id : "4bf92f3577b34da6a3ce929d0e0e4736" → the full story of that request across gateway, RFQ service, pricing, RabbitMQ consumer (Q55).
  4. Read the stack trace and surrounding INFO logs, check whether it is one client or everybody (remove the client filter, look at the histogram for a spike).
  5. Correlate with deployments or downstream outages (dashboards of error rate per service/version).
  • Dashboards (Lens visualizations): errors per service, top exception types, slowest endpoints, RFQs expired per hour.
  • Alerts / rules: notify Teams/Slack/email when ERROR count > N in 5 minutes or a specific exception appears.
  • Saved searches for common support questions; APM and Observability apps if Elastic APM agents are installed.
  • Make logs useful: structured JSON, consistent field names (ECS), traceId, business ids (rfqId, clientId), no secrets/PII.
Q90.What is DeployIT, and where does it fit in the delivery process?

Deployit (by XebiaLabs, later renamed XL Deploy, now Digital.ai Deploy) is an application release automation tool. It takes the artifacts CI produced and deploys them to environments (DEV, TEST, UAT, PROD) in a repeatable, audited, model-based way: you describe what should be deployed where, and it computes the steps (the deployment plan), including updates and rollbacks.

rfq-service 1.4.17 = JAR + config templates + SQL"]
  end
  PKG -->|import| XL[DeployIT / XL Deploy repository]
  XL --> ENVD[Environment DEV
hosts, app servers, K8s namespaces, dictionaries]
  XL --> ENVT[Environment TEST]
  XL --> ENVP[Environment PROD]
  XL -.->|"generated plan: stop → copy → configure → start → check"| ENVP
ConceptMeaning
Application / Deployment packagea versioned bundle of everything deployed (JARs, WARs, config files, SQL scripts, K8s/Helm resources); format DAR, described by deployit-manifest.xml
Infrastructure (containers)targets: hosts (SSH), Tomcat/WebLogic/JBoss servers, databases, Kubernetes, cloud
Environmenta named group of infrastructure (e.g. UAT = 2 hosts + 1 DB)

Deployment plansteps generated by comparing the package with what is deployed: initial install, upgrade (only changed parts), undeploy, rollback
Permissions & auditwho may deploy what to which environment, full history (important for banks: change management)

Where it fits: after CI. Jenkins builds and tests, publishes the artifact to Nexus and imports a deployment package into DeployIT; deployments to each environment are triggered from Jenkins (plugin or CLI), from Digital.ai Release (orchestration of approvals and release trains), or manually by an authorized person. It separates building software (CI) from deploying it (CD) and enforces "the same package in every environment".

Comparable tools: Octopus Deploy, Argo CD/Flux (GitOps for Kubernetes), Spinnaker, Ansible-based deploys, Helm.
