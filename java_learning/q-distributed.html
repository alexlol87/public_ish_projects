Q46–Q55: Distributed architecture & caching

Microservices trade-offs, CAP, communication styles, resilience, sagas, caching with Redis and Spring, scaling and observability.

Architecture

Q46.What are the pros and cons of microservices?

A microservice architecture splits an application into small services, each owning one business capability and its own data, deployed independently and talking over the network. The opposite is a monolith (one deployable); a "modular monolith" is a monolith with strict internal module boundaries.

flowchart LR
  subgraph Monolith
    M[One app: orders + pricing + users + billing] --> MDB[(One DB)]
  end
  subgraph Microservices
    O[orders] --> ODB[(orders DB)]
    P[pricing] --> PDB[(pricing DB)]
    U[users] --> UDB[(users DB)]
    O -- REST --> P
    O -- events --> MQ{{broker}} --> B[billing]
  end
Pros
  • Independent deployment and release cadence per team.
  • Scale only the hot parts (10 pricing pods, 2 user pods).
  • Fault isolation: billing down ≠ ordering down (if designed for it).
  • Technology freedom per service; smaller codebases easier to understand.
  • Team autonomy and clear ownership (Conway's law).
Cons
  • Distributed system problems: network latency and failures, timeouts, retries, partial failure.
  • No ACID transactions across services → sagas, eventual consistency.
  • Operational cost: CI/CD per service, containers, K8s, service discovery, config.
  • Observability becomes essential: tracing, centralized logs.
  • Harder testing (contract tests) and API versioning.
  • Risk of a "distributed monolith": services that must be deployed together.

Interview angle: microservices are an organizational scaling tool more than a technical one. Start with a well-modularized monolith unless you have several teams and clear domain boundaries.

Q47.Explain the CAP theorem.

In a distributed data store, when a network Partition happens (nodes can't talk to each other), you must choose between:

  • Consistency: every read gets the latest write (or an error). Formally: linearizability.
  • Availability: every request to a non-failing node gets a (non-error) response, possibly stale.

Partitions will happen, so P is not optional: the real choice is CP or AP during a partition.

flowchart LR
  subgraph DC1
    A[Node A
client writes x=2]
  end
  subgraph DC2
    B[Node B
still has x=1]
  end
  A -. network partition X .- B
  B --> Q{client reads x from B}
  Q -- CP --> E[refuse / error until partition heals
e.g. ZooKeeper, etcd, HBase, Mongo default majority]
  Q -- AP --> S[answer x=1, reconcile later
e.g. Cassandra, DynamoDB, Couchbase with low consistency]
  • PACELC extends it: if Partition → choose A or C; Else (normal operation) → choose Latency or Consistency. E.g. synchronous replication = consistent but slower.
  • Many systems are tunable: Cassandra's consistency level per query (ONE, QUORUM, ALL); QUORUM reads + writes give strong consistency.
  • A single-node relational DB is not really "distributed", so CAP doesn't apply to it; with replicas, async replication reads can be stale.
  • Don't confuse CAP's "C" with ACID's "C" (ACID C = constraints are respected).
Q48.How do services communicate, and when do you choose sync vs async?

Synchronous (request/response)

REST over HTTP (RestClient, WebClient, OpenFeign, HTTP interface clients), gRPC (HTTP/2 + Protobuf, fast, typed), GraphQL.

Caller waits for the answer. Simple, immediate result, easy to reason about. But: temporal coupling (callee must be up), latency adds up along the chain, cascading failures.

Asynchronous (messaging)

Message broker: RabbitMQ (queues, commands), Kafka (event log, streams). Also HTTP 202 + callback/polling.

Caller publishes and moves on. Decoupled in time, absorbs load spikes, enables fan-out to many consumers. But: eventual consistency, harder debugging, duplicates/ordering to handle, a broker to operate.

sequenceDiagram
  participant O as Orders
  participant P as Pricing
  participant MQ as Broker
  participant B as Billing
  participant N as Notifications
  O->>P: sync: GET /price (need the answer now)
  P-->>O: 200 price
  O->>MQ: async: publish OrderPlaced
  MQ-->>B: OrderPlaced
  MQ-->>N: OrderPlaced
Choose sync whenChoose async when
The caller needs the answer to continue (a query, a price, validation)The caller only needs to know it was accepted ("order received")
A user is waiting and the chain is shortWork is slow or can happen later (emails, reports, invoices)
Strong consistency is required right nowSeveral services react to the same event (fan-out)
Simple CRUD between two servicesLoad spikes must be smoothed; consumer may be down temporarily

Typical systems mix both: synchronous queries, asynchronous commands and events.

Q49.How do you make service-to-service calls resilient?

Assume every remote call can be slow, fail, or fail halfway. The patterns, drawn from the caller inwards in one common layering (it is a design choice: Resilience4j's annotations apply Retry outermost by default, then CircuitBreaker, then TimeLimiter, with Bulkhead innermost, configurable via the aspect-order properties):

// Resilience4j with Spring Boot (resilience4j-spring-boot3 + spring-boot-starter-aop, called spring-boot-starter-aspectj in Boot 4)
@Service
class PricingClient {
    @CircuitBreaker(name = "pricing", fallbackMethod = "cachedPrice")
    @Retry(name = "pricing")
    @Bulkhead(name = "pricing")
    public Price price(String sku) {
        return restClient.get().uri("/price/{sku}", sku).retrieve().body(Price.class);
    }
    private Price cachedPrice(String sku, Throwable t) { return cache.lastKnown(sku); }
}
resilience4j:
  circuitbreaker.instances.pricing:
    sliding-window-size: 20
    failure-rate-threshold: 50
    wait-duration-in-open-state: 30s
  retry.instances.pricing:
    max-attempts: 3
    wait-duration: 200ms
    enable-exponential-backoff: true
  bulkhead.instances.pricing:
    max-concurrent-calls: 20

Spring Framework 7 (Boot 4) also has built-in @Retryable and @ConcurrencyLimit (enable with @EnableResilientMethods) for simple cases. Remember: retries multiply load. 3 layers each retrying 3 times = 27 calls to the bottom service.

Q50.How do you handle a business transaction that spans several services?

Each service has its own database, so there is no single ACID transaction. Options:

  • Two-phase commit (2PC / XA): a coordinator asks all participants to "prepare", then "commit". Strongly consistent, but blocking, slow, coordinator is a single point of failure, and most brokers/NoSQL/HTTP services don't support it. Rarely used in microservices.
  • Saga: a sequence of local transactions; each step publishes an event/command that triggers the next. If a step fails, previously completed steps are undone by compensating transactions (refund, release stock). Eventually consistent.

Choreography

No central coordinator: services react to each other's events. Simple for 2–4 steps; the flow is implicit and hard to follow as it grows.

Orchestration

A saga orchestrator (a service or a workflow engine like Temporal, Camunda) tells each service what to do and handles compensation. Explicit flow, easier monitoring.

sequenceDiagram
  participant O as Order service (orchestrator)
  participant P as Payment
  participant I as Inventory
  participant S as Shipping
  O->>O: create order PENDING (local tx)
  O->>P: charge
  P-->>O: charged
  O->>I: reserve stock
  I-->>O: OUT OF STOCK
  Note over O: compensate the completed steps in reverse
  O->>P: refund (compensation)
  O->>O: order CANCELLED

The outbox pattern: publish reliably

Problem: "save to DB, then publish to RabbitMQ": if the app crashes between the two, the DB says yes but nobody hears about it (or you publish and the DB rolls back). Fix: write the event to an outbox table in the same local transaction; a relay (polling job or CDC with Debezium) publishes it afterwards.

flowchart LR
  S[Service] -->|one local transaction| T1[(orders table)]
  S -->|same transaction| T2[(outbox table)]
  R[Relay: scheduler or Debezium CDC] -->|reads unsent rows| T2
  R -->|publish, then mark sent| MQ{{RabbitMQ / Kafka}}
  • Delivery becomes at least once, so consumers must be idempotent (Q62).
  • Design for intermediate states visible to users (PENDING) and for compensations that can themselves fail (retry them).

Redis essentials

  • In-memory key-value store; command execution is single-threaded (so each command is atomic), I/O threads optional since Redis 6.
  • Data structures: String (cache values, counters INCR), Hash (object fields), List, Set, Sorted Set (leaderboards, rate limits by time), Stream, Pub/Sub, HyperLogLog, geo.
  • TTL per key (SET k v EX 600); eviction policy when memory is full (maxmemory-policy allkeys-lru, volatile-lru, allkeys-lfu, noeviction…).
  • Persistence: RDB snapshots and/or AOF log. High availability: replicas + Sentinel, or Redis Cluster (sharding over 16 384 hash slots).
  • Uses beyond caching: distributed locks (SET key token NX PX 30000, Redisson), rate limiting, session store (Spring Session), idempotency keys, leaderboards.
  • Spring: spring-boot-starter-data-redis (Lettuce client), RedisTemplate/StringRedisTemplate, RedisCacheManager for @Cacheable.

For "your Redis experience", describe a concrete use: what you cached, the key design (price:{sku}), TTLs, serialization (JSON vs JDK), how you invalidated, and a problem you solved (e.g. a stampede on a hot key).

Q52.How do you handle cache invalidation and consistency?

"There are only two hard things in computer science: cache invalidation and naming things." A cache is a copy; copies go stale. Decide how stale is acceptable per data type, then combine techniques:

  1. TTL: every entry expires. The safety net: even if everything else fails, staleness is bounded.
  2. Delete on write (cache-aside): update DB, then delete the key (not update it). Next read reloads. Do it after commit (@TransactionalEventListener(phase = AFTER_COMMIT)), or a concurrent reader may re-cache the old value.
  3. Event-driven invalidation: the owning service publishes ProductChanged; every instance/service evicts its copy. Needed for local (in-memory) caches on many pods.
  4. Versioned keys: product:42:v7; bumping the version makes old entries unreachable.
  5. CDC: Debezium streams DB changes → invalidations, catching writes that bypass your code.

The classic race (why "delete" and "after commit")

sequenceDiagram
  participant A as Reader A
  participant B as Writer B
  participant C as Cache
  participant D as DB
  A->>C: GET (miss)
  A->>D: read old value v1
  B->>D: write v2 + commit
  B->>C: DELETE key
  A->>C: SET key = v1 (stale! A read before B's write)
  Note over C: stale until TTL expires → keep TTLs as the safety net

The window is small but real; mitigations: short TTLs, "delayed double delete" (delete again a few hundred ms later), or versioned/compare-and-set writes.

Other problems to mention

  • Cache stampede (thundering herd): a hot key expires and 1 000 requests hit the DB at once. Fix: a lock/single-flight so only one request reloads (Caffeine does this per key; @Cacheable(sync = true)), early probabilistic refresh, jittered TTLs.
  • Cache penetration: requests for keys that don't exist always miss → cache "not found" briefly, or use a Bloom filter.
  • Avalanche: many keys expire at once (same TTL set at startup) → add random jitter to TTLs.
  • Never cache in a way that breaks correctness-critical reads (balances, stock at checkout): read those from the source of truth.

A common combo is a two-level cache: Caffeine (L1, short TTL) in front of Redis (L2).

Spring's cache abstraction

Annotations on methods, implemented with a proxy (AOP): before calling your method the proxy computes a key from the arguments and looks it up in a Cache from the configured CacheManager (Caffeine, Redis, …). The provider is swappable without changing your code.

flowchart LR
  C[Caller] --> P{Cache proxy:
key = sku}
  P -- hit --> C
  P -- miss --> M[your method: DB call] --> P
  P -- put result --> CM[(CacheManager → Caffeine / Redis)]

@Configuration
@EnableCaching
class CacheConfig {}   // with spring-boot-starter-cache + Caffeine/Redis on the classpath, Boot configures the CacheManager

@Service
class ProductService {
    @Cacheable(cacheNames = "products", key = "#id", unless = "#result == null")   // note: sync = true cannot be combined with unless
    public Product get(long id) { return repo.findById(id).orElse(null); }           // cached

    @CachePut(cacheNames = "products", key = "#p.id")
    public Product update(Product p) { return repo.save(p); }                        // always runs, refreshes cache

    @CacheEvict(cacheNames = "products", key = "#id")
    public void delete(long id) { repo.deleteById(id); }

    @CacheEvict(cacheNames = "products", allEntries = true)
    @Scheduled(fixedRate = 3_600_000)
    public void evictAll() {}
}
spring:
  cache:
    type: redis                 # or caffeine
    redis:
      time-to-live: 10m
    # caffeine:
    #   spec: maximumSize=10000,expireAfterWrite=5m
  • Same proxy pitfalls as @Transactional: self-invocation and private methods bypass the cache.
  • Cached objects must be serializable for Redis (configure a JSON serializer); returning a mutable cached object from a local cache lets callers modify the shared instance.
  • The abstraction has no TTL attribute; TTL is configured on the provider.

Operations

Q54.How do you scale a service horizontally?

Vertical scaling = bigger machine. Horizontal = more instances behind a load balancer. Horizontal scaling requires the service to be stateless: any instance can handle any request.

flowchart LR
  U[Clients] --> LB[Load balancer / K8s Service / Ingress]
  LB --> P1[pod 1]
  LB --> P2[pod 2]
  LB --> P3[pod 3 … added by HPA]
  P1 & P2 & P3 --> R[(Redis: sessions, cache, locks)]
  P1 & P2 & P3 --> DB[(DB primary + read replicas)]
  P1 & P2 & P3 --> MQ{{broker: competing consumers}}
  1. Make it stateless: no HTTP session in memory (use JWTs or Spring Session + Redis), no local files, no in-memory queues holding important work.
  2. Load balancing: round robin / least connections; health checks (readiness probe) so traffic only goes to ready pods.
  3. Autoscaling: Kubernetes HPA on CPU, or custom metrics (requests/s, queue depth with KEDA).
  4. Watch out for single-instance assumptions: @Scheduled jobs run on every pod (use ShedLock), in-memory caches diverge, synchronized doesn't lock across pods.
  5. Scale the bottleneck, which is usually the database: connection pool limits (pods × pool size ≤ DB max connections), read replicas, caching, partitioning/sharding, CQRS.
  6. Messaging: consumers scale as competing consumers on a queue (watch ordering, Q61).
  7. Graceful shutdown and fast startup so pods can come and go.
Q55.How do you make a distributed system observable?

Observability = being able to answer "what is going on and why?" from the outside. Three pillars, linked together by a trace ID:

Logs

Structured (JSON) logs with traceId, spanId, service, level. Shipped to a central store (ELK / Kibana, Loki/Grafana, Splunk). Boot 3.4+ supports structured logging: logging.structured.format.console=ecs.

Metrics

Numbers over time: request rate, error rate, latency percentiles, JVM memory, pool usage, queue depth. Micrometer → Prometheus → Grafana dashboards and alerts.

Traces

The path of one request across services as a tree of spans with timings. Micrometer Tracing (successor of Spring Cloud Sleuth) + OpenTelemetry → Zipkin / Jaeger / Tempo.

Plus

Health checks (Actuator), alerting on SLOs, dashboards per service (RED: Rate, Errors, Duration; USE: Utilization, Saturation, Errors), profiling.
