Core container

Q31.Explain IoC and dependency injection in Spring. What bean scopes exist?

IoC (Inversion of Control): instead of your objects creating their collaborators with new, a container (the ApplicationContext) creates them and controls their lifecycle. DI (Dependency Injection) is how IoC is done: the container passes ("injects") dependencies into an object.

Three injection styles:

// 1. Constructor injection (recommended): immutable, required, easy to unit test
@Service
class OrderService {
    private final OrderRepository repo;
    OrderService(OrderRepository repo) { this.repo = repo; }
}
// 2. Setter injection: optional dependencies
@Autowired void setAuditor(Auditor a) { this.auditor = a; }
// 3. Field injection: concise but hides dependencies, needs reflection in tests; avoid
@Autowired private OrderRepository repo;

When several beans match a type: @Primary marks the default, @Qualifier("name") picks one, injecting List<PaymentProvider> gets all of them, and ObjectProvider<T> gives lazy/optional access.

Bean scopes

ScopeInstancesUse
singleton (default)one per ApplicationContextservices, repositories, controllers. Must be thread-safe / stateless.
prototypenew one every time it is requested from the containerstateful helpers. Spring does not call destroy callbacks for prototypes.
requestone per HTTP requestrequest-specific data (web apps only)
sessionone per HTTP sessionuser's shopping cart in a server-rendered app
applicationone per ServletContextrare
websocketone per WebSocket sessionrare
Classic trap: prototype inside a singleton A prototype injected into a singleton is created once (when the singleton is built), so it behaves like a singleton. Fix: inject ObjectProvider<MyPrototype> and call getObject() each time, or use @Lookup. Request/session-scoped beans injected into singletons work because Spring injects a scoped proxy that resolves the current request's instance on each call.
Q32.How does Spring Boot auto-configuration work?

@SpringBootApplication includes @EnableAutoConfiguration. At startup Boot loads a list of auto-configuration classes from every JAR's META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports file (older versions used spring.factories; 2.7 introduced the .imports file and 3.0 dropped the old way). Each is a normal @Configuration class guarded by conditions; only those whose conditions pass contribute beans. Your own beans are processed first, so auto-configuration backs off when you define your own.

flowchart TD
  A["@EnableAutoConfiguration"] --> B[Read AutoConfiguration.imports from all JARs
e.g. DataSourceAutoConfiguration, JacksonAutoConfiguration ...]
  B --> C{"@ConditionalOnClass(DataSource, HikariDataSource)?
is the library on the classpath"}
  C -- no --> X[skip]
  C -- yes --> D{"@ConditionalOnMissingBean(DataSource)?
did the user define one"}
  D -- user defined one --> X2[back off: use the user's bean]
  D -- no --> E{"@ConditionalOnProperty(spring.datasource.url)…"}
  E --> F[create HikariDataSource from spring.datasource.* properties]

// A simplified auto-configuration you could write for your own company starter
@AutoConfiguration
@ConditionalOnClass(AuditClient.class)
@EnableConfigurationProperties(AuditProperties.class)
public class AuditAutoConfiguration {
    @Bean
    @ConditionalOnMissingBean                              // user can override
    @ConditionalOnProperty(prefix = "audit", name = "enabled", havingValue = "true", matchIfMissing = true)
    AuditClient auditClient(AuditProperties props) { return new AuditClient(props.url()); }
}
// + file src/main/resources/META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
//   containing: com.acme.audit.AuditAutoConfiguration

Other common conditions: @ConditionalOnBean, @ConditionalOnWebApplication, @ConditionalOnMissingClass, @ConditionalOnResource.

Debugging: run with --debug (or debug=true) to print the condition evaluation report (which auto-configs matched and why), or GET /actuator/conditions. Exclude one: @SpringBootApplication(exclude = DataSourceAutoConfiguration.class) or spring.autoconfigure.exclude.

Spring Boot 4 split auto-configuration into many smaller modules (one per technology, e.g. spring-boot-webmvc, spring-boot-jdbc), so the classpath holds only what your starters need; the mechanism above is unchanged.

@Component
class PriceCache implements InitializingBean, DisposableBean {
    PriceCache(PriceClient client) { ... }                        // 1
    @PostConstruct void warmUp() { ... }                          // 4: dependencies are injected now
    @Override public void afterPropertiesSet() { ... }            // 5

    @Override public void destroy() { ... }                       // 9

  • Before instances exist, BeanFactoryPostProcessors can modify bean definitions (e.g. resolving ${...} placeholders).
  • @PostConstruct runs before proxies exist: calling a @Transactional method of the same bean there gets no transaction. For "do something when the app is fully up" use @EventListener(ApplicationReadyEvent.class) or ApplicationRunner.
  • Prototype beans get steps 1–7 but never the destroy callbacks.
  • SmartLifecycle beans get start() after all singletons are ready and stop() early during shutdown (used for message listeners, schedulers; see the audit writer on page 4).
Q34.How does @Transactional work, and what are the pitfalls?

Spring wraps the bean in a proxy. On a call the proxy asks the PlatformTransactionManager (e.g. JpaTransactionManager) to begin a transaction, binds the connection/EntityManager to the current thread (ThreadLocal), calls your method, then commits, or rolls back if a RuntimeException/Error escapes.

sequenceDiagram
  participant C as Caller
  participant P as Proxy (TransactionInterceptor)
  participant TM as TransactionManager
  participant S as Your service
  C->>P: placeOrder()
  P->>TM: getTransaction(): BEGIN, bind connection to thread
  P->>S: placeOrder()
  S-->>P: returns / throws
  alt success or checked exception
    P->>TM: COMMIT
  else RuntimeException or Error
    P->>TM: ROLLBACK
  end
  P-->>C: result

Main attributes

  • propagation: REQUIRED (default: join existing or start new), REQUIRES_NEW (suspend the outer one, start an independent one, e.g. audit log that must persist even if the business tx rolls back), NESTED (savepoint), MANDATORY, SUPPORTS, NOT_SUPPORTED, NEVER.
  • isolation: DB isolation level (Q76).
  • readOnly = true: hint; Hibernate skips dirty checking and flushes, some drivers route to replicas.
  • rollbackFor / noRollbackFor, timeout.

Pitfalls

  1. Self-invocation: this.otherTransactionalMethod() bypasses the proxy, so its settings (e.g. REQUIRES_NEW) are ignored.
  2. Method visibility: private methods are never intercepted (keep transactional methods public; since Spring 6 protected/package-private work with class-based proxies, but private never does).
  3. Checked exceptions do not roll back by default. Use rollbackFor = Exception.class or throw unchecked exceptions.
  4. Catching the exception inside the method means the proxy never sees it → commit. And if an inner REQUIRED method threw and marked the tx rollback-only, the outer commit fails with UnexpectedRollbackException.
  5. Other threads: @Async, CompletableFuture, parallel streams run outside the transaction (it is in a ThreadLocal).
  6. Long transactions: calling a remote HTTP service or waiting on a queue inside a transaction holds a DB connection (and locks) the whole time. Keep transactions short; do remote calls before/after.
  7. The bean must be a Spring bean: objects created with new get no proxy.
  8. Sending messages/events before commit: if the tx then rolls back, the message is already out. Use @TransactionalEventListener(phase = AFTER_COMMIT) or the outbox pattern (Q50).
  9. Open Session in View (spring.jpa.open-in-view, true by default with a warning): keeps the persistence context open during view rendering, hiding lazy-loading problems and holding connections longer. Many teams set it to false.
@Service
class OrderService {
    private final AuditService audit;   // separate bean so REQUIRES_NEW goes through its proxy

    @Transactional(rollbackFor = Exception.class)
    public void placeOrder(Order o) throws PaymentException {
        repo.save(o);
        payments.charge(o);              // throws checked PaymentException → rollback thanks to rollbackFor
        audit.log("order placed");       // REQUIRES_NEW: committed even if placeOrder later rolls back
    }
}
@Service
class AuditService {
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void log(String msg) { ... }
}

Web: MVC, reactive, errors, config

Q35.Spring MVC vs WebFlux: when do you use each? What's your reactive experience?

The full explanation, with diagrams, is on page 2. The interview-length answer:

  • Spring MVC: Servlet stack, blocking, thread-per-request on Tomcat. Simple to write, debug and test; works with JPA/JDBC and every library. Default choice for CRUD and business services. Since Java 21, with spring.threads.virtual.enabled=true, it also scales to many concurrent I/O-bound requests.
  • Spring WebFlux: reactive, non-blocking, event loop on Netty, Mono/Flux. Use it when the whole chain is non-blocking (R2DBC, WebClient, reactive Mongo/Redis) and you need streaming (SSE, WebSockets), backpressure, gateways (Spring Cloud Gateway), or huge fan-out of remote calls with few threads.
  • Don't choose WebFlux and then call JDBC or blocking SDKs everywhere: you get the complexity without the benefit.

Answering "your reactive experience": talk about something concrete: e.g. "I wrote WebFlux endpoints returning Mono/Flux, used WebClient with timeout + retryWhen(Retry.backoff…), R2DBC repositories, tested with StepVerifier and WebTestClient, and fixed a production issue where a blocking call ran on the Netty event loop (moved it to boundedElastic, added BlockHound in tests)". The pitfalls you mention matter more than the list of operators.

Q36.What is backpressure, and what happens if you block inside a reactive chain?

Backpressure is the consumer telling the producer how much it can handle, so a fast producer cannot overwhelm a slow consumer. In Reactive Streams it is built into the protocol: the subscriber calls subscription.request(n) and the publisher may send at most n items.

sequenceDiagram
  participant Pub as Publisher (fast: DB cursor)
  participant Sub as Subscriber (slow: writes to a client)
  Sub->>Pub: request(10)
  Pub->>Sub: 10 × onNext
  Note over Sub: processes slowly, requests more only when ready
  Sub->>Pub: request(10)
  Pub->>Sub: 10 × onNext

When the source cannot slow down (mouse clicks, market ticks: a "hot" source), you choose a strategy: onBackpressureBuffer (bounded), onBackpressureDrop, onBackpressureLatest, or onBackpressureError. limitRate(n) controls the request batch size. Across the network, backpressure maps to TCP flow control.

Blocking inside a reactive chain

WebFlux runs your operators on a few Netty event-loop threads (≈ number of cores). A blocking call (JDBC, Thread.sleep, RestTemplate, .block()) freezes one of them, and with it every connection served by that loop. A handful of slow blocking calls can make the whole service unresponsive, throughput collapses, latency explodes, health checks time out.

  • .block() on a Reactor Netty thread throws IllegalStateException: block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-N.
  • Other blocking calls are not detected at runtime; use BlockHound in tests.
  • If you must call blocking code: Mono.fromCallable(() -> blockingCall()).subscribeOn(Schedulers.boundedElastic()).
Q37.How do you handle errors in a Spring REST API?

Goal: one consistent error format, correct HTTP status codes, no stack traces leaked to clients, and full details in the logs. Use a global @RestControllerAdvice and the standard Problem Details format (RFC 9457, application/problem+json), supported natively since Spring 6 via ProblemDetail.

flowchart LR
  C[Controller / Service throws] --> D[DispatcherServlet]
  D --> H{"@ExceptionHandler in the same controller?"}
  H -- no --> A{"@RestControllerAdvice handler?"}
  A -- yes --> P[ProblemDetail JSON + status]
  A -- no --> DEF[Spring default error handling → /error → 500]

public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(long id) { super("Order " + id + " not found"); }
}

@RestControllerAdvice
class GlobalExceptionHandler extends ResponseEntityExceptionHandler {   // handles Spring's own exceptions (400s) too

    @ExceptionHandler(OrderNotFoundException.class)
    ProblemDetail notFound(OrderNotFoundException ex) {
        ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
        pd.setTitle("Order not found");
        pd.setType(URI.create("https://errors.example.com/order-not-found"));
        return pd;
    }

    @ExceptionHandler(OptimisticLockingFailureException.class)
    ProblemDetail conflict(OptimisticLockingFailureException ex) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, "The order was modified by someone else, reload and retry");
    }

    @ExceptionHandler(Exception.class)
    ProblemDetail unexpected(Exception ex) {
        log.error("Unexpected error", ex);                                 // full details only in logs
        return ProblemDetail.forStatusAndDetail(HttpStatus.INTERNAL_SERVER_ERROR, "Unexpected error");
    }
}
{
  "type": "https://errors.example.com/order-not-found",
  "title": "Order not found",
  "status": 404,
  "detail": "Order 42 not found",
  "instance": "/orders/42"
}
  • Validation: @Valid @RequestBody → MethodArgumentNotValidException → 400; override handleMethodArgumentNotValid to list field errors.
  • Status mapping: 400 bad input, 401 not authenticated, 403 not allowed, 404 not found, 409 conflict, 422 business rule violated, 429 rate limited, 500 bug, 502/503/504 downstream problems.
  • Include a traceId in the response so support can find the logs (Q55).
  • spring.mvc.problemdetails.enabled=true makes Spring's built-in exceptions use ProblemDetail without writing an advice.
  • WebFlux: same @RestControllerAdvice, or operators like onErrorResume.
Q38.How do you manage configuration across environments?

Principle (from the "12-factor app"): build one artifact, configure it per environment from the outside. Never rebuild the JAR for prod.

flowchart BT
  A["application.yml inside the JAR (defaults)"] --> B["application-{profile}.yml (e.g. application-prod.yml)"]
  B --> C["external config file / config server / K8s ConfigMap"]
  C --> D["OS environment variables (SHOP_PAYMENT_TIMEOUT=5s)"]
  D --> E["Java system properties -D..."]
  E --> F["command-line args --server.port=9090 (highest)"]

(Simplified; higher in the picture overrides lower.)

  • Profiles: SPRING_PROFILES_ACTIVE=prod activates application-prod.yml and @Profile("prod") beans. Use profiles for environment differences, not for business features (use feature flags for those).
  • Type-safe properties: @ConfigurationProperties records with @Validated so the app fails fast at startup if a value is missing or wrong.
  • Secrets never in Git: environment variables from a vault (HashiCorp Vault, AWS Secrets Manager, K8s Secrets, Jenkins credentials), referenced as ${DB_PASSWORD}.
  • Centralized config: Spring Cloud Config Server (Git-backed), Consul, or K8s ConfigMaps mounted as files plus spring.config.import=optional:configtree:/etc/config/.
  • Refresh without restart: @RefreshScope (Spring Cloud) or just roll the pods.

Q40.Explain how Spring Security works.

Spring Security is a chain of servlet filters that runs before your controllers. Each filter does one job (CSRF, authentication, exception translation, authorization).

  DFP --> FCP[FilterChainProxy]
  FCP --> SFC{pick the first SecurityFilterChain
whose matcher fits the URL}
  SFC --> F1[CorsFilter / CsrfFilter]
  F1 --> F2[Authentication filter
e.g. BearerTokenAuthenticationFilter,
UsernamePasswordAuthenticationFilter]
  F2 --> F3[ExceptionTranslationFilter]
  F3 --> F4[AuthorizationFilter]

Authentication (who are you?):

flowchart LR
  F[Auth filter extracts credentials] --> AM[AuthenticationManager
ProviderManager]
  AM --> P1[DaoAuthenticationProvider
UserDetailsService + PasswordEncoder]
  AM --> P2[JwtAuthenticationProvider
JwtDecoder]
  P1 --> OK[Authenticated Authentication

  OK --> SC[SecurityContextHolder

  • Authentication: principal (who), credentials, authorities (ROLE_ADMIN, SCOPE_orders.read).
  • SecurityContextHolder: stores the Authentication in a ThreadLocal so any code in the request can read it (WebFlux: ReactiveSecurityContextHolder).
  • Authorization (what may you do?): URL rules in the filter chain (AuthorizationFilter) plus method security (@PreAuthorize).
  • ExceptionTranslationFilter turns AuthenticationException into 401 and AccessDeniedException into 403.
@Configuration
@EnableWebSecurity
class SecurityConfig {
    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())                              // stateless REST API with tokens, no cookies
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/actuator/health/**").permitAll()
                .requestMatchers(HttpMethod.GET, "/orders/**").hasAuthority("SCOPE_orders.read")
                .requestMatchers("/admin/**").hasRole("ADMIN")
                .anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(Customizer.withDefaults()));
        return http.build();
    }
}

Defaults when you just add the starter: everything requires authentication, a generated user password is logged, form login + HTTP Basic, CSRF protection on, security headers added.

Q41.How do you secure a microservice with OAuth2/JWT and method-level rules?

The microservice is an OAuth2 Resource Server: it does not log users in, it only validates the access token (a JWT) that an Authorization Server (Keycloak, Okta, Entra ID, Spring Authorization Server) issued.

sequenceDiagram
  participant U as User / client app
  participant AS as Authorization server (Keycloak)
  participant GW as API gateway
  participant S as Orders service (resource server)
  U->>AS: login (OIDC authorization code + PKCE)
  AS-->>U: access token (JWT, signed with private key, expires in 5 min)
  U->>GW: GET /orders  Authorization: Bearer eyJ...
  GW->>S: forwards the token
  S->>AS: (once, cached) GET JWKS public keys
  S->>S: verify signature, exp, iss, aud → build Authentication with authorities from scopes/roles
  S-->>U: 200 or 401/403

A JWT has three Base64URL parts: header.payload.signature. Payload claims: sub (user id), iss (issuer), aud (audience), exp (expiry), scope, custom roles. The service validates it locally with the issuer's public key: no call per request.

spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: https://auth.example.com/realms/shop   # discovers the JWKS URL, validates "iss"
          audiences: orders-api                               # validates "aud" (Boot 3.2+)
@Configuration
@EnableMethodSecurity                    // turns on @PreAuthorize / @PostAuthorize
class SecurityConfig {
    @Bean
    SecurityFilterChain chain(HttpSecurity http) throws Exception {
        return http
            .authorizeHttpRequests(a -> a.anyRequest().authenticated())
            .oauth2ResourceServer(o -> o.jwt(j -> j.jwtAuthenticationConverter(keycloakRoles())))
            .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .csrf(c -> c.disable())
            .build();
    }

    // By default "scope" claim → SCOPE_xxx authorities. Map Keycloak realm roles → ROLE_xxx too:
    private Converter<Jwt, AbstractAuthenticationToken> keycloakRoles() {
        var conv = new JwtAuthenticationConverter();
        var scopes = new JwtGrantedAuthoritiesConverter();                 // keep the default SCOPE_xxx mapping
        conv.setJwtGrantedAuthoritiesConverter(jwt -> {
            Map<String, Object> realm = jwt.getClaimAsMap("realm_access");
            List<String> roles = realm == null ? List.of() : (List<String>) realm.getOrDefault("roles", List.of());
            List<GrantedAuthority> all = new ArrayList<>(scopes.convert(jwt));
            roles.forEach(r -> all.add(new SimpleGrantedAuthority("ROLE_" + r)));
            return all;
        });
        return conv;
    }
}

@Service
class OrderService {
    @PreAuthorize("hasRole('TRADER') or hasAuthority('SCOPE_orders.read')")
    public Order get(long id) { ... }

    @PreAuthorize("#customerId == authentication.name")         // only your own orders (SpEL with method args)
    public List<Order> forCustomer(String customerId) { ... }

    @PostAuthorize("returnObject.ownerId == authentication.name")   // check the result

  • Keep access tokens short-lived; revocation is hard with JWTs (they are valid until exp).
  • Test with spring-security-test: mockMvc.perform(get("/orders/1").with(jwt().authorities(new SimpleGrantedAuthority("SCOPE_orders.read")))).

Batch, testing, JPA

Q42.What is Spring Batch, and what are its main concepts?

A framework for large, non-interactive, bulk data processing: end-of-day trade files, nightly reconciliation, migrating millions of rows. It gives you chunked transactions, restartability, skip/retry, and a metadata store recording every run.

flowchart LR
  JL[JobLauncher / JobOperator] -->|run with JobParameters| J[Job: endOfDayJob]
  J --> S1[Step 1: importTrades
chunk-oriented]
  J --> S2[Step 2: reconcile]
  J --> S3[Step 3: sendReport
tasklet]
  S1 --> R[ItemReader
FlatFileItemReader] --> P[ItemProcessor
validate / transform] --> W[ItemWriter
JdbcBatchItemWriter]
  JR[(JobRepository: BATCH_JOB_INSTANCE,
JOB_EXECUTION, STEP_EXECUTION tables)]
  J -.records state.-> JR
  S1 -.records read/write counts, commit points.-> JR
ConceptMeaning
JobThe whole batch process, a sequence (or flow) of steps.
JobInstanceA logical run: job + identifying JobParameters (e.g. date=2026-11-23).
JobExecutionOne attempt to run a JobInstance (a failed instance can have several executions).
Step / StepExecutionAn independent phase of the job, and one attempt of it.
Chunk-oriented stepRead items one by one, process each, write them in chunks of N inside one transaction.
Tasklet stepA single action (delete a file, call a procedure).
ExecutionContextKey/value state saved at each commit (e.g. reader position) → enables restart.
JobRepositoryStores all of the above in database tables.
// Spring Batch 5 style (Boot 3). Batch 6 (Boot 4) keeps the concepts; some builder methods changed.
@Configuration
class EodJobConfig {
    @Bean
    Job endOfDayJob(JobRepository repo, Step importTrades, Step sendReport) {
        return new JobBuilder("endOfDayJob", repo)
                .start(importTrades)
                .next(sendReport)
                .build();
    }

    @Bean
    Step importTrades(JobRepository repo, PlatformTransactionManager tx,
                      FlatFileItemReader<TradeCsv> reader, TradeProcessor processor, JdbcBatchItemWriter<Trade> writer) {
        return new StepBuilder("importTrades", repo)
                .<TradeCsv, Trade>chunk(500, tx)       // 500 items per transaction
                .reader(reader)
                .processor(processor)                   // return null to filter an item out
                .writer(writer)
                .faultTolerant()
                .skip(ValidationException.class).skipLimit(100)
                .retry(TransientDataAccessException.class).retryLimit(3)
                .build();
    }
}
Q43.How does Spring Batch handle failures and restarts?
  • Chunk transactions: if writing chunk #7 fails, only chunk #7 is rolled back; chunks 1–6 are committed.
  • State at every commit: the step's ExecutionContext (e.g. "read 3 000 lines") is saved in the JobRepository in the same transaction as the chunk.
  • Restart: launching the same JobInstance (same identifying parameters) again creates a new JobExecution that skips steps already COMPLETED and resumes the failed step from the last saved position. Readers implementing ItemStream (most built-in ones) restore their position.
  • A completed JobInstance cannot be re-run with the same parameters (JobInstanceAlreadyCompleteException). For "run every day", use a date parameter or a RunIdIncrementer.
  • Skip: .skip(X.class).skipLimit(n) skips bad records (e.g. a malformed line) up to n; skipped items can be logged with a SkipListener.
  • Retry: .retry(X.class).retryLimit(n) for transient errors (deadlock, timeout).
  • When a skippable error happens during write, Batch rolls back the chunk and re-processes it item by item ("scan" mode) to find the bad item.
  • allowStartIfComplete(true) on a step forces it to re-run on restart; startLimit(n) limits attempts.
  • A crashed process leaves the execution in STARTED; you must mark it FAILED (or use JobOperator) before restarting.
sequenceDiagram
  participant Op as Operator / scheduler
  participant B as Spring Batch
  participant JR as JobRepository
  Op->>B: run endOfDayJob(date=2026-11-23)
  B->>JR: JobInstance #1, Execution #1
  B->>B: step importTrades: chunks 1..6 committed
  B--xB: chunk 7 fails (DB down)
  B->>JR: Execution #1 FAILED, read.count = 3000
  Op->>B: run endOfDayJob(date=2026-11-23) again
  B->>JR: same JobInstance #1, new Execution #2
  B->>B: resume importTrades at item 3001
  B->>JR: Execution #2 COMPLETED
Q44.How do you test Spring Boot applications?

The test pyramid: many fast unit tests, fewer slice tests, few full integration tests.

flowchart TB
  E2E["Few: end-to-end / contract tests"]
  INT["Some: @SpringBootTest + Testcontainers (real DB, RabbitMQ), WireMock for HTTP"]

Q45.What is the N+1 problem in JPA, and how do you fix it?

You run 1 query to load N parents, then Hibernate runs N more queries to load each parent's lazy association when you touch it. 100 orders → 101 queries.

@Entity class Order {
    @Id Long id;
    @ManyToOne(fetch = FetchType.LAZY) Customer customer;
    @OneToMany(mappedBy = "order") List<OrderLine> lines;     // LAZY by default
}

List<Order> orders = orderRepository.findAll();           // 1 query: select * from orders
for (Order o : orders) {
    o.getLines().size();                                   // N queries: select * from order_line where order_id = ?
}
sequenceDiagram
  participant App
  participant DB
  App->>DB: SELECT * FROM orders   (returns 100)
  loop for each of the 100 orders
    App->>DB: SELECT * FROM order_line WHERE order_id = ?
  end
  Note over App,DB: 101 round trips instead of 1 or 2

Detect it: enable SQL logging (spring.jpa.show-sql or logging.level.org.hibernate.SQL=debug), Hibernate statistics, or assert query counts in tests.

Fixes

// 1. JOIN FETCH in JPQL: one query
@Query("select distinct o from Order o join fetch o.lines where o.status = :s")
List<Order> findWithLines(@Param("s") Status s);

// 2. Entity graph: same effect, declarative
@EntityGraph(attributePaths = {"lines", "customer"})
List<Order> findByStatus(Status s);

// 3. Batch fetching: N queries become N/size queries (where order_id in (?, ?, ... 50))
@BatchSize(size = 50) @OneToMany(mappedBy = "order") List<OrderLine> lines;
// or globally: spring.jpa.properties.hibernate.default_batch_fetch_size=50

// 4. DTO projection: load exactly what the screen needs, no entities at all
@Query("select new com.shop.OrderSummary(o.id, c.name, count(l)) from Order o join o.customer c join o.lines l group by o.id, c.name")
List<OrderSummary> summaries();
  • JOIN FETCH of a collection + pagination: Hibernate paginates in memory (warning HHH90003004). Fetch IDs page first, then fetch details for those IDs, or use batch fetching.
  • Don't fetch two List collections at once with JOIN FETCH (MultipleBagFetchException, and a Cartesian product).
  • Don't "fix" it with FetchType.EAGER: eager is applied everywhere and can cause N+1 itself.
