synchronized

Every Java object has a built-in lock called a monitor. synchronized acquires it on entry and releases it on exit (also when an exception is thrown). Only one thread at a time can hold a given monitor; others wait in BLOCKED state.

public class Inventory {
    private final Map<String, Integer> stock = new HashMap<>();
    private final Object lock = new Object();            // private lock object: nobody outside can lock it

    public synchronized int count(String sku) {          // locks "this"
        return stock.getOrDefault(sku, 0);
    }

    public boolean reserve(String sku, int qty) {
        synchronized (lock) {                            // block: keep the critical section small
            int left = stock.getOrDefault(sku, 0);
            if (left < qty) return false;
            stock.put(sku, left - qty);                  // check + update happen atomically
            return true;
        }
    }

    public static synchronized void resetAll() { }       // static: locks Inventory.class
}
  • Reentrant: a thread already holding the lock can enter another synchronized method of the same object.
  • Visibility: releasing the monitor publishes all writes to the next thread that acquires it (happens-before).
  • No timeout, cannot be interrupted while waiting, no fairness, one condition (wait/notify) per monitor.
  • Virtual threads: on Java 21–23 blocking inside synchronized pins the carrier thread. Fixed in Java 24 (JEP 491), so on Java 25 synchronized is fine with virtual threads.
In Spring Boot A synchronized method on a singleton bean serializes all requests through it, and it protects only this JVM. With 3 pods, three threads can be inside "the same" synchronized block at once. For data in a database use transactions with optimistic/pessimistic locking; for cluster-wide mutual exclusion use a distributed lock (ShedLock, Redis/Redisson, DB advisory locks).

ReentrantLock

An explicit lock object from java.util.concurrent.locks with the same semantics as synchronized (mutual exclusion, reentrancy, happens-before) plus extra features.

private final ReentrantLock lock = new ReentrantLock();      // new ReentrantLock(true) = fair (FIFO), slower

public void update() {
    lock.lock();                 // ALWAYS lock() before try …
    try {
        // critical section
    } finally {
        lock.unlock();           // … and unlock() in finally, or a thrown exception leaves it locked forever
    }
}

Variations

// ReadWriteLock: many readers OR one writer. Good when reads vastly outnumber writes.
private final ReentrantReadWriteLock rw = new ReentrantReadWriteLock();
private Map<String, Rate> rates = Map.of();
Rate get(String ccy) { rw.readLock().lock(); try { return rates.get(ccy); } finally { rw.readLock().unlock(); } }
void reload(Map<String, Rate> fresh) { rw.writeLock().lock(); try { rates = fresh; } finally { rw.writeLock().unlock(); } }

// StampedLock (Java 8): adds optimistic reads (no locking at all if no writer interfered). Not reentrant.
private final StampedLock sl = new StampedLock();
double distance() {
    long stamp = sl.tryOptimisticRead();
    double cx = x, cy = y;
    if (!sl.validate(stamp)) {            // a writer came in: fall back to a real read lock
        stamp = sl.readLock();
        try { cx = x; cy = y; } finally { sl.unlockRead(stamp); }
    }
    return Math.hypot(cx, cy);
}

Note: for the reload example above, a volatile reference to an immutable map is simpler and faster than a ReadWriteLock (see volatile).

tryLock

tryLock() returns immediately: true if it got the lock, false if someone else holds it. tryLock(timeout, unit) waits at most that long (and is interruptible). This lets a thread give up instead of waiting forever, which prevents deadlocks and lets you degrade gracefully.

flowchart LR
  A[tryLock 200ms] -->|true| B[do work] --> C[unlock in finally]
  A -->|false| D[fallback: return cached value,
skip, retry later with jitter, or 409/429]

@Service
public class FxRateService {
    private final ReentrantLock refreshLock = new ReentrantLock();
    private volatile Rates cached = Rates.EMPTY;           // readers never lock
    private final RatesClient client;

    public FxRateService(RatesClient client) { this.client = client; }

    public Rates current() {
        if (cached.isStale() && refreshLock.tryLock()) {   // only ONE request thread refreshes…
            try {
                if (cached.isStale()) cached = client.fetch();   // re-check inside the lock
            } finally {
                refreshLock.unlock();
            }
        }
        return cached;                                     // …everybody else gets the current value immediately
    }
}

// Deadlock-free money transfer with timeouts
boolean transfer(Account a, Account b, BigDecimal amt) throws InterruptedException {
    long deadline = System.nanoTime() + TimeUnit.SECONDS.toNanos(1);
    while (System.nanoTime() < deadline) {
        if (a.lock.tryLock(50, TimeUnit.MILLISECONDS)) {
            try {
                if (b.lock.tryLock(50, TimeUnit.MILLISECONDS)) {
                    try { a.debit(amt); b.credit(amt); return true; }
                    finally { b.lock.unlock(); }
                }
            } finally { a.lock.unlock(); }
        }
        Thread.sleep(ThreadLocalRandom.current().nextInt(5, 20));   // random backoff avoids livelock
    }
    return false;
}
Only call unlock() if tryLock returned true; unlocking a lock you don't hold throws IllegalMonitorStateException.

volatile

volatile guarantees visibility and ordering for one variable: every read sees the latest write (from any thread), and writes before a volatile write cannot be reordered after it. It does not make compound actions atomic.

Good uses
  • Stop/enable flags written by one thread.
  • Publishing an immutable object: volatile Config current; then current = newConfig;
  • Double-checked locking for lazy singletons.
Not enough for
  • count++ (read-modify-write) → use Atomic.
  • check-then-act on several fields → use a lock.
  • Making the contents of a mutable object thread-safe (volatile is about the reference only).
@Component
public class MaintenanceMode {
    private volatile boolean enabled;          // set by an admin endpoint, read by every request thread
    public boolean isEnabled() { return enabled; }
    public void set(boolean on) { enabled = on; }
}

@Component
public class PricingRules {
    // copy-on-write publishing: build a new immutable snapshot, swap the reference
    private volatile List<Rule> rules = List.of();
    public List<Rule> rules() { return rules; }
    @Scheduled(fixedDelay = 60_000)
    void reload() { rules = List.copyOf(repository.loadRules()); }   // readers see the old OR the new list, never half
}

// Double-checked locking: the volatile is essential (without it another thread could see a half-constructed object)
class Lazy {
    private static volatile ExpensiveClient instance;
    static ExpensiveClient get() {
        var local = instance;
        if (local == null) {
            synchronized (Lazy.class) {
                local = instance;
                if (local == null) instance = local = new ExpensiveClient();
            }
        }
        return local;
    }
}

In Spring you rarely need double-checked locking: beans are already singletons created once at startup.

Atomic classes

AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference<V>, the array variants, and the accumulators LongAdder/LongAccumulator. They are lock-free: built on CPU compare-and-swap (CAS).

AtomicLong requests = new AtomicLong();
requests.incrementAndGet();                         // ++x atomically
requests.getAndAdd(5);                              // x += 5, returns the old value
requests.updateAndGet(v -> Math.max(v, 100));       // any function (must be side-effect free: it may run several times)
requests.accumulateAndGet(7, Long::sum);

AtomicBoolean started = new AtomicBoolean();
if (started.compareAndSet(false, true)) { initOnce(); }   // exactly one thread wins

// AtomicReference: swap whole immutable snapshots atomically
record Stats(long count, long totalMs) { Stats add(long ms) { return new Stats(count + 1, totalMs + ms); } }
AtomicReference<Stats> stats = new AtomicReference<>(new Stats(0, 0));
stats.updateAndGet(s -> s.add(elapsedMs));          // both fields change together, consistently

// LongAdder: many threads incrementing a hot counter (metrics). Spreads updates over cells, sums on read.
LongAdder hits = new LongAdder();
hits.increment();
long total = hits.sum();                             // not an atomic snapshot while updates continue
  • AtomicLong vs LongAdder: under heavy contention CAS retries pile up; LongAdder avoids them. Use AtomicLong when you need compareAndSet or an exact value on every read (e.g. ID generation).
  • ABA problem: CAS sees A, someone changes A→B→A, CAS succeeds wrongly. Rarely matters in Java (GC means references aren't reused while you hold them); AtomicStampedReference adds a version if it does.
  • In Spring Boot, prefer Micrometer counters for metrics (meterRegistry.counter("orders.created").increment()), which are thread-safe and exported to Prometheus.

CompletableFuture

A Future you can compose: describe "when this finishes, do that", combine several, handle errors, without blocking a thread in between.

flowchart LR
  A[supplyAsync: load customer] --> C{thenCombine}
  B[supplyAsync: load orders] --> C
  C --> D[thenApply: build view]
  D --> E[exceptionally / handle: fallback]
  E --> F[join or return to Spring]

@Service
public class DashboardService {
    private final CustomerClient customers;
    private final OrderClient orders;
    private final ExecutorService io = Executors.newVirtualThreadPerTaskExecutor();   // or an injected Spring TaskExecutor

    public DashboardService(CustomerClient customers, OrderClient orders) { this.customers = customers; this.orders = orders; }

    public Dashboard load(long id) {
        CompletableFuture<Customer> c = CompletableFuture.supplyAsync(() -> customers.find(id), io);
        CompletableFuture<List<Order>> o = CompletableFuture.supplyAsync(() -> orders.recent(id), io)
                .completeOnTimeout(List.of(), 500, TimeUnit.MILLISECONDS);      // fallback after 500 ms

        return c.thenCombine(o, Dashboard::new)                                  // both in parallel: ~max, not sum, of the 2 latencies
                .exceptionally(ex -> Dashboard.unavailable(id))                  // any failure → fallback
                .join();                                                         // wait here (fine on a virtual / request thread)
    }
}

thenCombine(other, fn)combine two independent futureszip

// Fan out to N calls and collect
List<CompletableFuture<Price>> futures = skus.stream()
        .map(sku -> CompletableFuture.supplyAsync(() -> pricing.price(sku), io)).toList();
List<Price> prices = CompletableFuture.allOf(futures.toArray(CompletableFuture[]::new))
        .thenApply(v -> futures.stream().map(CompletableFuture::join).toList())
        .join();

// Dependent calls
CompletableFuture<Invoice> inv = findOrder(id)              // CF<Order>
        .thenCompose(order -> billing.invoiceFor(order));  // CF<Invoice> (not CF<CF<Invoice>>)
Pitfalls
  • Without an executor, supplyAsync uses ForkJoinPool.commonPool() (cores − 1 threads), shared by the whole JVM including parallel streams. Blocking I/O there starves everyone. Always pass an executor for I/O.
  • Exceptions are wrapped in CompletionException; use ex.getCause().
  • A future whose exception nobody handles fails silently.
  • cancel(true) does not interrupt the running task (unlike FutureTask).
  • ThreadLocal context (transactions, security, MDC) is not propagated; see page 1.
  • Spring MVC controllers may return CompletableFuture<T>: the request thread is released and the response is written when the future completes.

Sealed classes (not concurrency, but asked)

A sealed class or interface lists exactly which classes may extend/implement it (final since Java 17). Combined with records and pattern matching for switch (final in Java 21), the compiler knows every possible subtype, so a switch can be exhaustive without a default: add a new subtype and every switch that forgot it stops compiling.

classDiagram
  class PaymentResult {
    <<sealed interface>>
  }
  class Approved {
    <<record>>
    String transactionId
  }
  class Declined {
    <<record>>
    String reason
  }
  class Pending {
    <<record>>
    Duration retryAfter
  }
  PaymentResult <|.. Approved
  PaymentResult <|.. Declined
  PaymentResult <|.. Pending

public sealed interface PaymentResult permits Approved, Declined, Pending {}
public record Approved(String transactionId) implements PaymentResult {}   // records are implicitly final
public record Declined(String reason)        implements PaymentResult {}
public record Pending(Duration retryAfter)   implements PaymentResult {}
// Subclasses must be final, sealed, or non-sealed (= open again for extension).

@Service
class PaymentService {
    PaymentResult pay(Order o) { ... }
}

@RestController
class PaymentController {
    private final PaymentService service;
    PaymentController(PaymentService service) { this.service = service; }

    @PostMapping("/payments")
    ResponseEntity<?> pay(@RequestBody Order o) {
        return switch (service.pay(o)) {                                     // exhaustive: no default needed
            case Approved(String txId)       -> ResponseEntity.ok(Map.of("tx", txId));            // record pattern
            case Declined(String reason)     -> ResponseEntity.unprocessableEntity().body(reason);
            case Pending(Duration after)     -> ResponseEntity.accepted()
                                                     .header("Retry-After", String.valueOf(after.toSeconds())).build();
        };
    }
}

Why it is useful around concurrency: async code passes messages and results between threads. Sealed hierarchies of immutable records are ideal for that: thread-safe by construction, and the compiler checks every handler covers every case.

sealed interface Command permits Deposit, Withdraw, Shutdown {}
record Deposit(long cents) implements Command {}
record Withdraw(long cents) implements Command {}
record Shutdown() implements Command {}

// One consumer thread owns the balance: no locks needed at all (the "actor" style)
void loop(BlockingQueue<Command> inbox) throws InterruptedException {
    long balance = 0;
    while (true) {
        switch (inbox.take()) {
            case Deposit d  -> balance += d.cents();
            case Withdraw w -> balance -= w.cents();
            case Shutdown s -> { return; }
        }
    }
}

For JSON, Jackson needs to know the subtypes: @JsonTypeInfo(use = JsonTypeInfo.Id.NAME, property = "type") + @JsonSubTypes on the sealed interface.

Virtual threads in depth

Virtual threads (final in Java 21, JEP 444) are java.lang.Thread instances scheduled by the JVM onto a small pool of carrier platform threads (a ForkJoinPool with parallelism = CPU cores). When a virtual thread blocks on I/O, a lock, sleep or a BlockingQueue, the JVM unmounts it (its stack frames move to the heap) and the carrier runs another one. See the picture on page 1.

try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    IntStream.range(0, 100_000).forEach(i ->
        executor.submit(() -> { Thread.sleep(Duration.ofSeconds(1)); return i; }));
}   // ≈ 1 second total with 100 000 virtual threads; with a 200-thread pool it would take ≈ 500 s

Thread vt = Thread.ofVirtual().name("import-", 0).start(task);
vt.isVirtual();   // true

Do's and don'ts

DoDon't
Create one per task; they are cheap.Pool them (a pool of virtual threads makes no sense).
Write plain blocking code (JDBC, RestClient, Thread.sleep).Use them for CPU-bound work: they don't add cores; use a fixed pool or parallel streams.
Limit access to scarce resources with a Semaphore or the connection pool size.Use thread pool size as a rate limiter: there is no pool any more.
Use ReentrantLock or (Java 24+) synchronized.Store big objects in ThreadLocals: there may be millions of threads (prefer ScopedValue).
Find pinning with JFR event jdk.VirtualThreadPinned.Expect lower latency for a single request: they improve throughput, not speed.

Pinning

A virtual thread is pinned when it cannot unmount while blocked, so it blocks its carrier too. Since there are only ~cores carriers, a few pinned threads can stall the app.

  • Java 21–23: blocking inside synchronized (or in Object.wait()) pinned. Common workaround: replace with ReentrantLock.
  • Java 24+ (so Java 25): fixed by JEP 491; synchronized no longer pins.
  • Still pins on all versions: blocking while a native method (JNI) or a foreign function call is on the stack, and class initialization.

In Spring Boot

spring.threads.virtual.enabled: true   # Boot 3.2+, needs Java 21+
  • Tomcat (and Jetty) handle each request on a new virtual thread.
  • @Async, @Scheduled, Spring AMQP / Kafka listeners and others use virtual-thread executors (SimpleAsyncTaskExecutor/SimpleAsyncTaskScheduler).
  • Because virtual threads are daemon threads, set spring.main.keep-alive=true if the app has no web server and only scheduled jobs, or the JVM may exit.
  • Your bottleneck moves to the DB connection pool and downstream services: protect them (Hikari pool size, Semaphore, Spring Framework 7's @ConcurrencyLimit, Resilience4j bulkheads).
@Service
class ExternalApi {
    private final Semaphore permits = new Semaphore(20);     // at most 20 concurrent calls to the partner API
    Response call(Request r) throws InterruptedException {
        permits.acquire();
        try { return client.send(r); } finally { permits.release(); }
    }
}
