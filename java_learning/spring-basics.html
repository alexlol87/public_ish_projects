Spring Boot basics

The foundation the rest of the site builds on: what Spring actually does for you, what a bean is, how a request flows through your code, and why "proxy" and "singleton" matter so much for concurrency.

Spring vs. Spring Boot

Spring Framework

A set of libraries. Its heart is the IoC container (the ApplicationContext) that creates your objects and plugs them into each other. Around it: Spring MVC and WebFlux (web), transaction management, data access, AOP, events, scheduling, caching abstraction.

On its own you had to configure all of this yourself (XML or Java config, deploy a WAR into a Tomcat).

Spring Boot

Opinionated defaults on top of Spring:

  • Starters: one dependency (spring-boot-starter-web) pulls a whole tested set of libraries.
  • Auto-configuration: "Jackson is on the classpath and you didn't define an ObjectMapper? I'll create one."
  • Embedded server: Tomcat or Netty inside your JAR; you run java -jar app.jar.
  • Externalized config (application.yml, profiles, env vars) and Actuator (health, metrics).

IoC and dependency injection

Without Spring, every class builds what it needs. It is hard to test (you cannot swap the real database for a fake) and every class knows how to construct the others:

public class OrderService {
    private final OrderRepository repo = new JdbcOrderRepository(new HikariDataSource(...)); // hard-wired
    private final PaymentClient payments = new PaymentClient("https://pay...");             // hard-wired
}

With Spring, the class just declares what it needs in its constructor, and the container gives it the objects (inversion of control: you no longer control creation, the container does):

@Service                       // "Spring, please create one instance of this and manage it"
public class OrderService {
    private final OrderRepository repo;
    private final PaymentClient payments;

    // Constructor injection: Spring sees one constructor and passes the beans in. No @Autowired needed.
    public OrderService(OrderRepository repo, PaymentClient payments) {
        this.repo = repo;
        this.payments = payments;
    }
}

Prefer constructor injection Fields can be final, the object is never half-built, and in a unit test you just call new OrderService(fakeRepo, fakePayments). Field injection (@Autowired private Repo repo;) hides dependencies and needs reflection in tests.

Beans and stereotype annotations

Spring finds your classes by component scanning: it scans the package of your @SpringBootApplication class and all sub-packages for these annotations:

AnnotationLayerExtra behaviour
@ComponentGenericNone. The others are specializations of it.
@ServiceBusiness logicNone (documentation only).
@RepositoryData accessTranslates database exceptions into Spring's DataAccessException hierarchy.
@Controller / @RestControllerWebMethods handle HTTP requests. @RestController = @Controller + @ResponseBody (return values become JSON).
@Configuration + @BeanConfigMethods that return objects you want as beans, typically for third-party classes you cannot annotate.
@Configuration
public class HttpConfig {
    @Bean // the returned object becomes a bean named "restClient"
    RestClient restClient(RestClient.Builder builder) {   // Boot auto-configures the Builder
        return builder.baseUrl("https://payments.example.com").build();
    }
}

A minimal but complete Spring Boot app

<!-- pom.xml (the important parts) -->
<parent>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-parent</artifactId>
  <version>4.0.0</version>      <!-- pins versions of hundreds of libraries (a BOM) -->
</parent>
<properties><java.version>25</java.version></properties>
<dependencies>
  <dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-webmvc</artifactId></dependency> <!-- "starter-web" in Boot 3 -->
  <dependency><groupId>org.springframework.boot</groupId><artifactId>spring-boot-starter-data-jpa</artifactId></dependency>
  <dependency><groupId>com.h2database</groupId><artifactId>h2</artifactId><scope>runtime</scope></dependency>
</dependencies>
@SpringBootApplication   // = @SpringBootConfiguration + @EnableAutoConfiguration + @ComponentScan
public class ShopApplication {
    public static void main(String[] args) {
        SpringApplication.run(ShopApplication.class, args); // starts the container and the embedded Tomcat
    }
}

@Entity                               // JPA: this class maps to table "product"
class Product {
    @Id @GeneratedValue Long id;
    String name;
    BigDecimal price;
    protected Product() {}            // JPA needs a no-arg constructor
    Product(String name, BigDecimal price) { this.name = name; this.price = price; }
}

interface ProductRepository extends JpaRepository<Product, Long> {   // Spring Data writes the implementation
    List<Product> findByNameContainingIgnoreCase(String part);         // query derived from the method name
}

record ProductDto(Long id, String name, BigDecimal price) {}            // what the API returns

@Service
class ProductService {
    private final ProductRepository repo;
    ProductService(ProductRepository repo) { this.repo = repo; }

    @Transactional(readOnly = true)
    List<ProductDto> search(String q) {
        return repo.findByNameContainingIgnoreCase(q).stream()
                   .map(p -> new ProductDto(p.id, p.name, p.price)).toList();
    }
}

@RestController
@RequestMapping("/products")
class ProductController {
    private final ProductService service;
    ProductController(ProductService service) { this.service = service; }

    @GetMapping                                   // GET /products?q=phone
    List<ProductDto> search(@RequestParam String q) { return service.search(q); }
}

What happens at startup

flowchart TB
  A["java -jar app.jar → main() → SpringApplication.run()"] --> B[Read config: application.yml, profiles, env vars, command line]
  B --> C[Component scan: find @Component / @Service / @Controller / @Configuration classes]
  C --> D[Auto-configuration: evaluate @Conditional rules, add default beans]
  D --> E[Create bean definitions, then instantiate singletons in dependency order]
  E --> F[BeanPostProcessors wrap beans in proxies: @Transactional, @Async, @Cacheable, security]
  F --> G[Start embedded web server: Tomcat on port 8080 or Netty]
  G --> H[ApplicationReadyEvent: app is serving traffic]

How one HTTP request flows through Spring MVC

This is the single most useful diagram for understanding threads in Spring MVC: the same Tomcat worker thread carries the request through every layer, waits on the database, and writes the response.

sequenceDiagram
  autonumber
  participant Cl as Client
  participant T as Tomcat (thread http-nio-8080-exec-7)
  participant F as Filters (Security, logging)
  participant D as DispatcherServlet
  participant Ctl as @RestController
  participant Svc as @Service (proxy)
  participant DB as Database
  Cl->>T: GET /products?q=phone
  T->>F: same thread
  F->>D: same thread
  D->>D: HandlerMapping finds controller method
  D->>Ctl: argument resolvers bind @RequestParam, @RequestBody
  Ctl->>Svc: service.search("phone")
  Svc->>DB: SQL (thread BLOCKS while waiting)
  DB-->>Svc: rows
  Svc-->>Ctl: List of DTO
  Ctl-->>D: return value
  D-->>T: HttpMessageConverter (Jackson) writes JSON
  T-->>Cl: 200 OK + JSON
  • DispatcherServlet: the "front controller": the single servlet that receives every request and routes it to your controller method.
  • HandlerMapping: finds which method matches URL + HTTP verb.
  • HttpMessageConverter: converts JSON ↔ Java objects (Jackson).
  • Tomcat has a pool of worker threads (default max 200, property server.tomcat.threads.max). With 200 slow requests in flight, request 201 waits in the queue. That limit is the reason virtual threads and WebFlux exist (pages 1 and 2).

Proxies and AOP: the magic behind the annotations

When a bean has @Transactional, @Async, @Cacheable, @PreAuthorize…, the bean other classes receive is not your object, it is a proxy (a generated subclass, made with CGLIB) that wraps it:

The self-invocation trap 
@Service
class ReportService {
    public void generateAll() {
        for (var id : ids) generate(id);   // this.generate(): NO proxy → no @Async, no new transaction!
    }
    @Async @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void generate(long id) { ... }
}
Fix: move generate to another bean and inject it.

Beans are singletons, so they are shared by all threads

By default there is one instance of each bean, and every request thread calls it at the same time. So:

Wrong: mutable state in a singleton 
@Service
class PriceService {
    private BigDecimal lastPrice;          // shared by 200 threads!
    BigDecimal quote(String sku) {
        lastPrice = load(sku);             // thread A writes
        return lastPrice.multiply(FX);     // thread B may have overwritten it
    }
}
Right: keep state in local variables 
@Service
class PriceService {
    private final PriceRepository repo;    // final, injected, itself thread-safe
    BigDecimal quote(String sku) {
        BigDecimal price = load(sku);      // local: each thread has its own stack
        return price.multiply(FX);
    }
}

When you really need shared mutable state (counters, caches), use the tools from page 3.
