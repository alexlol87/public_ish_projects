Q67.What is Elasticsearch, and what are its core concepts?

Elasticsearch (ES) is a distributed search and analytics engine built on Apache Lucene, with a JSON REST API. It stores JSON documents and makes them searchable in near real time: full-text search with relevance ranking, filters, aggregations (analytics), geo queries, and (newer) vector search. It is the "E" in the ELK stack (Q89).

Q68.What is an inverted index, and why is Elasticsearch fast at search?

A normal (forward) index maps document → words. An inverted index maps term → list of documents containing it (a "posting list"), like the index at the back of a book.

Why ES is fast:

  • Lookup instead of scan: a LIKE '%fox%' in SQL reads every row; ES jumps straight to the term's posting list. Term dictionaries are compressed and searched like a sorted dictionary (FST structures in Lucene).
  • Analysis at index time: the expensive text processing is done once when writing.
  • Immutable segments: no locking for reads, OS file cache friendly, heavily compressed.
  • Doc values (columnar storage) make sorting and aggregations fast.
  • Filter caching: yes/no filters are cached as bitsets (Q70).
  • Distribution: shards are searched in parallel on several nodes and results merged.

The trade-offs: writes are heavier (analysis, segment merges), updates are delete + reinsert, it's near real-time (≈ 1 s), and it is not a transactional primary store.

Q70.Explain match vs term queries, and query vs filter context.

match (full text)

Analyzes the search text with the field's analyzer, then searches the resulting terms. "Quick Foxes" → quick OR fox (operator configurable). Use on text fields.

term (exact)

No analysis: looks up the exact term as given. Use on keyword, numbers, dates, booleans. terms = any of a list; range for numbers/dates.

Query context

"How well does this document match?" Computes a relevance _score (BM25). Used in must and should of a bool query.

Filter context

"Does it match, yes/no?" No scoring → faster, and results are cached. Used in filter and must_not.

GET /products/_search
{
  "query": {
    "bool": {
      "must":   [ { "match": { "name": "noise cancelling headphones" } } ],   // scored
      "should": [ { "match": { "tags": "bestseller" } } ],                   // boosts score if present
      "filter": [                                                            // not scored, cached
        { "term":  { "status": "ACTIVE" } },
        { "range": { "price": { "gte": 50, "lte": 300 } } }
      ],
      "must_not": [ { "term": { "brand": "NoName" } } ]
    }
  },
  "sort": [ "_score", { "price": "asc" } ],
  "aggs": { "by_brand": { "terms": { "field": "brand" } } }
}

Rule: put everything that is yes/no (status, dates, ranges, tenant, permissions) in filter; only the user's free-text in must/should.

Q71.When would you use Elasticsearch instead of a relational database?

Usually in addition to, not instead of: the relational DB stays the source of truth, ES is a read model optimized for search.

Use Elasticsearch for
  • Full-text search with relevance ranking, typo tolerance (fuzzy), synonyms, stemming, highlighting, autocomplete.
  • Faceted search: filter + counts per brand/price bucket in one call.
  • Logs, metrics and events: huge append-only volume, time-based queries, dashboards (ELK).
  • Search across many fields of denormalized documents with sub-second latency at large scale.
  • Geo search, vector/semantic search.
Keep the RDBMS for
  • Transactions and strong consistency (money, orders, stock).
  • Relational integrity, joins, constraints.
  • Data that must be visible immediately after write.
  • Frequent updates to the same records.
  • Being the durable system of record (ES can lose recent writes in some failure modes; re-indexing must be possible).
Q72.How would you integrate Elasticsearch into a Spring application?

Reading/writing: Spring Data Elasticsearch (spring-boot-starter-data-elasticsearch), built on the official Elasticsearch Java client (the old RestHighLevelClient is gone).

@Document(indexName = "products")
public class ProductDoc {
    @Id private String id;
    @Field(type = FieldType.Text, analyzer = "english") private String name;
    @Field(type = FieldType.Keyword) private String status;
    @Field(type = FieldType.Double) private double price;
    // getters/setters
}

public interface ProductSearchRepository extends ElasticsearchRepository<ProductDoc, String> {
    List<ProductDoc> findByNameAndStatus(String name, String status);      // derived query
}

@Service
class ProductSearch {
    private final ElasticsearchOperations ops;
    ProductSearch(ElasticsearchOperations ops) { this.ops = ops; }

    SearchHits<ProductDoc> search(String text, double maxPrice) {
        NativeQuery q = NativeQuery.builder()
            .withQuery(qb -> qb.bool(b -> b
                .must(m -> m.match(mt -> mt.field("name").query(text)))
                .filter(f -> f.term(t -> t.field("status").value("ACTIVE")))
                .filter(f -> f.range(r -> r.number(n -> n.field("price").lte(maxPrice))))))
            .withPageable(PageRequest.of(0, 20))
            .build();
        return ops.search(q, ProductDoc.class);
    }
}

SQL & Oracle

Q73.Explain the types of SQL joins.

Example data: customers (1 Ana, 2 Bob, 3 Cris) and orders (o1 → customer 1, o2 → customer 1, o3 → customer 9 which doesn't exist).

-- INNER JOIN: only matching pairs → Ana-o1, Ana-o2
SELECT c.name, o.id FROM customers c JOIN orders o ON o.customer_id = c.id;

-- LEFT (OUTER) JOIN: all customers, orders if any → Ana-o1, Ana-o2, Bob-NULL, Cris-NULL
SELECT c.name, o.id FROM customers c LEFT JOIN orders o ON o.customer_id = c.id;

-- RIGHT JOIN: all orders, customer if any → Ana-o1, Ana-o2, NULL-o3
-- FULL OUTER JOIN: everything from both → Ana-o1, Ana-o2, Bob-NULL, Cris-NULL, NULL-o3

-- CROSS JOIN: every combination (3 × 3 = 9 rows), e.g. generate all size × colour variants
SELECT s.size, c.colour FROM sizes s CROSS JOIN colours c;

-- SELF JOIN: a table with itself, e.g. employee and their manager
SELECT e.name, m.name AS manager FROM employees e LEFT JOIN employees m ON e.manager_id = m.id;

-- ANTI JOIN: customers WITHOUT orders → Bob, Cris
SELECT c.* FROM customers c WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
-- SEMI JOIN: customers WITH at least one order (each once) → Ana
SELECT c.* FROM customers c WHERE EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.id);
  • A condition on the right table in WHERE turns a LEFT JOIN into an INNER JOIN (NULLs are filtered out); put it in the ON clause instead.
  • Oracle's old outer join syntax: WHERE o.customer_id(+) = c.id; prefer ANSI LEFT JOIN.
  • Physical join algorithms the optimizer picks: nested loops (small inputs, indexed), hash join (large, equality), merge join (sorted inputs).
  • Beware NOT IN with a subquery that can return NULL: returns no rows at all. Use NOT EXISTS.
Q74.How do indexes work, and when can they hurt?

An index is a separate sorted data structure that maps column values to row locations (Oracle: ROWID), so the DB can find rows without scanning the whole table. The default is a B-tree (balanced tree): finding a value takes a few page reads even for billions of rows.

flowchart TB
  R["root: < 500 | >= 500"] --> B1["branch: < 200 | 200-499"]
  R --> B2["branch: 500-799 | >= 800"]
  B1 --> L1["leaf: 1 … 199 → rowids"]
  B1 --> L2["leaf: 200 … 499 → rowids"]
  B2 --> L3["leaf: 500 … 799 → rowids"]
  B2 --> L4["leaf: 800 … → rowids"]
  L1 --- L2 --- L3 --- L4

Leaves are linked, so range scans (BETWEEN, >, ORDER BY) are efficient too.

Kinds of indexes

  • Unique (enforces uniqueness; created for primary keys).
  • Composite (customer_id, created_at): usable for queries on customer_id, or customer_id + created_at, but generally not on created_at alone (leftmost-prefix rule; Oracle has "skip scan" as a partial exception). Put equality columns first, then range columns.
  • Covering: contains all columns the query needs → no table access (index-only scan).
  • Function-based (Oracle) / expression index (Postgres): CREATE INDEX users_email_upper ON users (UPPER(email)).
  • Bitmap (Oracle): low-cardinality columns in data warehouses; terrible for concurrent OLTP updates.
  • Postgres extras: GIN (JSONB, full text, arrays), GiST, BRIN (huge naturally ordered tables), partial indexes (WHERE status = 'OPEN').

When indexes hurt or don't help

  • Writes get slower: every INSERT/UPDATE/DELETE must update every index; more redo/WAL, more locking.
  • Storage and memory: indexes compete for buffer cache.
  • Low selectivity: WHERE gender = 'F' returning 50 % of rows: a full scan is faster than millions of random index lookups; the optimizer ignores the index (or wrongly uses it with stale stats).
  • Index not usable because of the query: function on the column (WHERE TRUNC(created) = …, UPPER(name)), implicit type conversion (varchar_col = 123), leading wildcard (LIKE '%abc'), OR across columns, !=, wrong column order in a composite index.
  • Redundant / unused indexes: cost without benefit (find them with usage monitoring).
  • Indexes on columns that are updated constantly, and sequence-based keys causing "hot" right-most leaf blocks under heavy concurrent inserts (Oracle: reverse key indexes, hash partitioning).
  • Missing index on foreign key columns: slow joins, and in Oracle table-level locks on the child when the parent is updated/deleted.

Typical fixes:

  • Add or fix an index (right columns, right order, covering), or rewrite the predicate so the index is usable (created >= DATE '2026-11-23' AND created < DATE '2026-11-24' instead of TRUNC(created) = …).
  • Gather statistics / histograms so the optimizer estimates correctly.
  • Select only needed columns; paginate with keyset pagination (WHERE id > :last ORDER BY id FETCH FIRST 50 ROWS ONLY) instead of huge OFFSETs.
  • Rewrite: EXISTS instead of IN with large subqueries, avoid SELECT DISTINCT hiding a bad join, avoid correlated subqueries per row, use window functions.
  • Fix the application side: N+1 (Q45), missing batching, fetch size (Oracle JDBC default fetch size is 10 rows → many round trips: set hibernate.jdbc.fetch_size).
  • Use bind variables (JDBC ?) so Oracle reuses plans instead of hard-parsing each literal. Watch for bind peeking issues with skewed data.
  • Bigger levers: partitioning, materialized views, caching, archiving old data.

Read phenomena

  • Dirty read: reading another transaction's uncommitted change (which may roll back).
  • Non-repeatable read: reading the same row twice gives different values because someone committed in between.
  • Phantom read: re-running a query returns new/missing rows because someone inserted/deleted matching rows.
  • (Also: lost update, write skew, see Q80.)

  • Oracle: supports READ COMMITTED (default) and SERIALIZABLE (plus READ ONLY). Uses MVCC with undo: readers never block writers and writers never block readers; each statement sees a consistent snapshot as of its start. Dirty reads are impossible. Oracle's SERIALIZABLE is really snapshot isolation (can fail with ORA-08177 "can't serialize access").
  • PostgreSQL: default READ COMMITTED; REPEATABLE READ is snapshot isolation (no phantoms either); SERIALIZABLE is true serializable (SSI), may abort with serialization failures that you retry. READ UNCOMMITTED behaves like READ COMMITTED.
  • Spring: @Transactional(isolation = Isolation.SERIALIZABLE); higher isolation → more aborts/locking → handle retries.

Q78.What is PL/SQL, and when would you put logic in the database?

PL/SQL (Procedural Language/SQL) is Oracle's procedural extension of SQL: variables, IF, loops, exceptions, cursors, and named units stored and executed inside the database: procedures, functions, packages (spec + body, grouping related code and state), and triggers.

CREATE OR REPLACE PACKAGE billing AS
  PROCEDURE close_month(p_month IN DATE);
END billing;
/
CREATE OR REPLACE PACKAGE BODY billing AS
  PROCEDURE close_month(p_month IN DATE) IS
    TYPE t_ids IS TABLE OF accounts.id%TYPE;
    l_ids t_ids;
  BEGIN
    SELECT id BULK COLLECT INTO l_ids                -- fetch many rows in one go
      FROM accounts WHERE status = 'ACTIVE';

    FORALL i IN 1 .. l_ids.COUNT                     -- one PL/SQL→SQL context switch for all inserts
      INSERT INTO invoices(account_id, month, amount)
      SELECT l_ids(i), p_month, SUM(amount) FROM usage
       WHERE account_id = l_ids(i) AND used_at >= p_month AND used_at < ADD_MONTHS(p_month, 1);

    COMMIT;
  EXCEPTION
    WHEN OTHERS THEN
      ROLLBACK;
      RAISE;                                         -- re-throw to the caller
  END close_month;
END billing;
/
// Calling it from Spring
new SimpleJdbcCall(jdbcTemplate).withCatalogName("billing").withProcedureName("close_month")
    .execute(Map.of("p_month", LocalDate.of(2026, 11, 1)));
// or Spring Data JPA: @Procedure(procedureName = "billing.close_month")
Logic in the DB makes sense for
  • Set-based, data-heavy processing (month-end, reconciliation, bulk transformations): moving millions of rows to the app and back is slow.
  • Reducing network round trips for chatty sequences of statements.
  • Integrity rules that must hold for every client of the DB (constraints first; triggers sparingly).
  • Existing legacy systems and data warehouses / ETL.
Prefer the application for
  • Business rules that change often: Java is easier to version, review, unit test, debug and deploy.
  • Scalability: app servers scale horizontally cheaply; the DB is the expensive shared bottleneck.
  • Portability: PL/SQL locks you into Oracle.
  • Calls to other systems, complex orchestration.
  • Hidden side effects (triggers surprise developers and ORMs).
Q79.What are window (analytic) functions? Give an example.

A window function computes a value for each row using a set of related rows (the "window"), without collapsing rows like GROUP BY does. Syntax: function() OVER (PARTITION BY … ORDER BY … [frame]).

-- 1. Running total and share of the desk total per trade
SELECT desk, trade_id, trade_time, amount,
       SUM(amount) OVER (PARTITION BY desk ORDER BY trade_time)  AS running_total,
       ROUND(100 * amount / SUM(amount) OVER (PARTITION BY desk), 1) AS pct_of_desk
FROM trades;

-- 2. Top 3 trades per desk (the classic "top N per group")
SELECT * FROM (
  SELECT t.*, ROW_NUMBER() OVER (PARTITION BY desk ORDER BY amount DESC) AS rn
  FROM trades t
) WHERE rn <= 3;

-- 3. Price change vs previous tick per instrument
SELECT instrument, tick_time, price,
       price - LAG(price) OVER (PARTITION BY instrument ORDER BY tick_time) AS change
FROM prices;

-- 4. Latest row per key (deduplicate)
SELECT * FROM (
  SELECT c.*, ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY updated_at DESC) rn FROM customer_versions c
) WHERE rn = 1;

-- 5. 7-row moving average (frame clause)
SELECT day, revenue, AVG(revenue) OVER (ORDER BY day ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma7
FROM daily_revenue;
FunctionGivesTies (amounts 300, 200, 200, 100)
ROW_NUMBER()unique sequence1, 2, 3, 4
RANK()rank with gaps1, 2, 2, 4
DENSE_RANK()rank without gaps1, 2, 2, 3
LAG/LEAD(col, n)value from n rows before/after
FIRST_VALUE/LAST_VALUE, NTILE(n)first/last in window, bucket number

Note: with ORDER BY in the window and no explicit frame, the default frame is "from the start to the current row" (RANGE), which is what makes running totals work, and why LAST_VALUE surprises people. Window functions are evaluated after WHERE/GROUP BY, so to filter on them you wrap them in a subquery.

Q80.How do you handle concurrent updates to the same row?

The problem is the lost update: two transactions read the same row, both compute a new value from what they read, and the second write silently overwrites the first.

sequenceDiagram
  participant A as Tx A (seller 1)
  participant DB as stock row: qty = 10
  participant B as Tx B (seller 2)
  A->>DB: SELECT qty → 10
  B->>DB: SELECT qty → 10
  A->>DB: UPDATE qty = 10 - 3 = 7, COMMIT
  B->>DB: UPDATE qty = 10 - 5 = 5, COMMIT
  Note over DB: qty = 5, should be 2. A's update is lost.

1. Atomic update in SQL (best when possible)

UPDATE stock SET qty = qty - :n WHERE sku = :sku AND qty >= :n;   -- 0 rows updated → not enough stock

The database does read + write under the row lock in one statement. No race, no retries.

2. Optimistic locking (version column)

Assume conflicts are rare. Each row has a version; updates check it hasn't changed.

UPDATE account SET balance = :newBalance, version = version + 1 WHERE id = :id AND version = :readVersion;
-- 0 rows → someone else changed it → reload and retry, or tell the user (HTTP 409)
@Entity
class Account {
    @Id Long id;
    BigDecimal balance;
    @Version Long version;        // Hibernate adds "and version = ?" and increments it automatically
}
// conflict → ObjectOptimisticLockingFailureException → retry the whole transaction (e.g. @Retryable) or return 409

3. Pessimistic locking (lock the row while you work)

Assume conflicts are frequent or retries are expensive. Others wait (or fail fast).

SELECT * FROM account WHERE id = :id FOR UPDATE;            -- waits for the lock
SELECT * FROM account WHERE id = :id FOR UPDATE NOWAIT;     -- error immediately if locked (Oracle ORA-00054)
SELECT * FROM account WHERE id = :id FOR UPDATE WAIT 3;     -- Oracle: wait max 3 s
SELECT * FROM jobs WHERE status = 'NEW' ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED;  -- PostgreSQL work-queue pattern: skip rows others hold
-- (Oracle also has SKIP LOCKED, but not combined with FETCH FIRST: open a cursor FOR UPDATE SKIP LOCKED and fetch 10)
public interface AccountRepository extends JpaRepository<Account, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)                     // SELECT ... FOR UPDATE
    @QueryHints(@QueryHint(name = "jakarta.persistence.lock.timeout", value = "3000"))
    @Query("select a from Account a where a.id = :id")
    Account lockById(@Param("id") long id);
}

@Transactional          // the lock lives until the transaction commits: keep it SHORT
public void withdraw(long id, BigDecimal amount) {
    Account a = repo.lockById(id);
    if (a.balance.compareTo(amount) < 0) throw new InsufficientFunds();
    a.balance = a.balance.subtract(amount);
}

Other tools

  • Isolation level SERIALIZABLE: the DB detects conflicts and aborts one transaction; retry it.
  • Unique constraints to prevent duplicates (instead of check-then-insert).
  • Single writer: route all updates for one key through one queue/consumer (Q61).
  • HTTP APIs: ETag + If-Match headers expose optimistic locking to clients (412 Precondition Failed).
  • Remember: Java locks (synchronized) don't help with several app instances; the database is the right place to coordinate (page 3).
