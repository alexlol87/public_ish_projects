1. Multithreading in Java 25 & Spring Boot

From "what is a thread" to the Java Memory Model, thread pools, ScopedValue and structured concurrency, and how all of it shows up in a Spring Boot service.

Process, thread, core

  • Process: a running program with its own memory. Your Spring Boot app is one process.
  • Thread: a path of execution inside a process. All threads share the heap; each has its own stack (local variables, method calls).
  • Platform thread: a Java Thread backed 1:1 by an OS thread. Costly: ~1 MB of reserved stack, slow to create, a few thousand per machine is the practical limit.
  • Virtual thread (Java 21+): a lightweight thread managed by the JVM, not the OS. Millions are fine. See below and page 3.

Concurrency vs. parallelism

A web server is mainly about concurrency: thousands of requests in flight that mostly wait (on the database, on other services). Number crunching (image processing, big reports) is about parallelism: keep every core busy.

Creating and running threads

// 1. The raw way (fine for learning, rarely right in production code)
Thread t = new Thread(() -> System.out.println("hi from " + Thread.currentThread().getName()));
t.start();       // start() creates the new thread; calling run() would just run it on the CURRENT thread
t.join();        // wait until it finishes

// 2. Builders (Java 21+)
Thread p = Thread.ofPlatform().name("worker-", 0).start(() -> work());   // worker-0
Thread v = Thread.ofVirtual().name("v-", 0).start(() -> work());         // virtual thread
Thread.startVirtualThread(() -> work());                                   // shortcut

// 3. The normal way: give tasks to an ExecutorService (a thread pool) and get Futures back
try (ExecutorService pool = Executors.newFixedThreadPool(4)) {      // ExecutorService is AutoCloseable since Java 19
    Future<Integer> f = pool.submit(() -> expensiveCalc());         // Callable<Integer>: returns a value, may throw
    pool.execute(() -> fireAndForget());                            // Runnable: no result
    Integer result = f.get(2, TimeUnit.SECONDS);                    // blocks up to 2s; throws TimeoutException
}                                                                   // close() waits for submitted tasks to finish

// 4. One virtual thread per task (Java 21+): the modern default for blocking I/O work
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<String>> pages = urls.stream().map(u -> exec.submit(() -> http.get(u))).toList();
}

Good to know when reading a thread dump RUNNABLE does not mean "on a CPU right now"; it means "ready or running" (a thread blocked in native socket read also shows as RUNNABLE). BLOCKED only happens with synchronized; a thread waiting for a ReentrantLock shows as WAITING (parked).

Thread pools in depth

Creating a platform thread is expensive, so we reuse them: a pool of worker threads takes tasks from a queue. Every Executors.newXxx factory is a pre-configured ThreadPoolExecutor:

ThreadPoolExecutor pool = new ThreadPoolExecutor(
    4,                                   // corePoolSize: threads kept alive even when idle
    16,                                  // maximumPoolSize: upper limit
    60, TimeUnit.SECONDS,                // extra (non-core) threads die after 60s idle
    new ArrayBlockingQueue<>(100),       // bounded work queue
    Thread.ofPlatform().name("report-", 0).factory(),
    new ThreadPoolExecutor.CallerRunsPolicy()   // when everything is full: run the task on the caller (natural backpressure)
);

What happens when you submit() a task. This order surprises many people: the queue fills up before extra threads are created.

How big should a pool be?

  • CPU-bound work: about Runtime.getRuntime().availableProcessors() threads. More only adds context switching.
  • I/O-bound work (Brian Goetz's formula): threads ≈ cores × (1 + waitTime / computeTime). 8 cores, requests that wait 90 ms and compute 10 ms → 8 × 10 = 80 threads.
  • Or skip the maths for I/O-bound work and use virtual threads, limiting the resource (DB connections, a Semaphore) instead of the threads.

Race conditions: why shared state breaks

count++ looks like one step, but it is three: read count, add 1, write back. Two threads can interleave:

class Counter {
    private int count;
    void increment() { count++; }          // NOT thread-safe
    int get() { return count; }
}

var c = new Counter();
try (var exec = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) exec.submit(c::increment);
}
System.out.println(c.get());   // often 9 9xx, rarely 10 000

// Fixes (details on page 3):
synchronized void increment() { count++; }        // mutual exclusion
private final AtomicInteger count = new AtomicInteger(); count.incrementAndGet();   // lock-free CAS
private final LongAdder hits = new LongAdder(); hits.increment();                  // best under heavy contention

Typical race conditions in real code:

  • Check-then-act: if (!map.containsKey(k)) map.put(k, v); → use map.putIfAbsent / computeIfAbsent on a ConcurrentHashMap.
  • Read-modify-write: counters, balances → atomics, locks, or let the database do it (UPDATE … SET qty = qty - 1, see Q80).
  • Non-thread-safe objects shared in a singleton: SimpleDateFormat, HashMap, ArrayList. Use DateTimeFormatter (immutable) and concurrent collections.

The Java Memory Model (JMM): visibility and ordering

Even without lost updates there is a second problem: visibility. Each core has its own caches and the JIT compiler and CPU may reorder instructions. A value written by one thread may not be seen by another thread, ever, unless there is a happens-before relationship.

class Worker implements Runnable {
    private boolean running = true;           // add volatile to fix
    public void run() { while (running) { /* work */ } }   // JIT may hoist the read: while(true)
    public void stop() { running = false; }   // may never be seen by the worker thread
}

Happens-before rules you need to know

If action X happens-before Y, then everything X (and anything before X in its thread) wrote is visible to Y.

  • Monitor lock: unlocking a synchronized block / Lock happens-before every later lock of the same monitor.
  • volatile: a write to a volatile field happens-before every later read of it.
  • Thread start / join: t.start() happens-before anything in t; everything in t happens-before t.join() returns.
  • Executors & concurrent collections: submitting a task happens-before it runs; putting into a BlockingQueue / ConcurrentHashMap happens-before the take/get that sees it; completing a Future happens-before get() returns.
  • final fields: correctly constructed objects' final fields are visible to all threads without synchronization (that is why immutable objects and records are thread-safe for free).
Rule of thumb Shared mutable state must be either (1) guarded by a lock, (2) volatile (if only one thread writes, or writes don't depend on the old value), (3) atomic, or (4) not shared/not mutable at all. Option 4 (immutable records, local variables, message passing) is the easiest to get right.

// Classic deadlock: two transfers in opposite directions
void transfer(Account from, Account to, BigDecimal amount) {
    synchronized (from) {
        synchronized (to) {        // T1: A→B locks A then B; T2: B→A locks B then A → both stuck forever
            from.debit(amount); to.credit(amount);
        }
    }
}

ThreadLocal and ScopedValue

A ThreadLocal gives every thread its own copy of a variable. Spring uses it everywhere, and that is why understanding it explains many Spring "mysteries":

  • SecurityContextHolder: the logged-in user of the current request.
  • TransactionSynchronizationManager: the current transaction / DB connection.
  • RequestContextHolder: the current HTTP request.
  • SLF4J/Logback MDC: traceId and other fields printed in every log line.
Consequence: context does not follow you to another thread If you call @Async, CompletableFuture.supplyAsync or start a thread, the new thread has no transaction, no security context and no MDC unless something copies them (Spring's TaskDecorator, Micrometer context propagation, DelegatingSecurityContextExecutor). And in a pool, always remove() a ThreadLocal after use, or the next task on that thread sees stale data.
private static final ThreadLocal<String> TENANT = new ThreadLocal<>();
try {
    TENANT.set("acme");
    service.handle();       // anything down the call stack can call TENANT.get()
} finally {
    TENANT.remove();        // essential in pooled threads
}

ScopedValue (final in Java 25, JEP 506)

The modern replacement for many ThreadLocal uses: an immutable value bound for the duration of a call, automatically unbound afterwards, cheap with millions of virtual threads, and inherited by subtasks of structured concurrency.

static final ScopedValue<String> TENANT = ScopedValue.newInstance();

void handle(Request req) {
    ScopedValue.where(TENANT, req.tenant())     // bind
               .run(() -> service.process());   // visible only inside this call (and its forked subtasks)
}                                               // unbound here automatically: no leaks, no remove()

// anywhere down the stack:
String tenant = TENANT.get();                   // NoSuchElementException if not bound; TENANT.isBound() to check

Interruption and cancellation

Java has no safe way to "kill" a thread. Instead you ask it to stop with interrupt(); blocking methods (sleep, wait, BlockingQueue.take, Future.get…) then throw InterruptedException.

public void run() {
    while (!Thread.currentThread().isInterrupted()) {
        try {
            Job job = queue.take();       // throws InterruptedException when interrupted
            process(job);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();   // restore the flag so callers know
            return;                               // and stop
        }
    }
}
// Never: catch (InterruptedException e) { }   ← swallows the stop request

ExecutorService.shutdownNow() and Future.cancel(true) interrupt the worker threads. Spring calls shutdown on its executors when the context closes (graceful shutdown: server.shutdown=graceful is the default since Boot 3.4).

Structured concurrency (preview in Java 25)

Problem: you fan out to 2 services in parallel. If one fails, the other should be cancelled; if the caller is cancelled, both should be. With plain executors this is easy to get wrong (leaked threads that keep running). StructuredTaskScope treats subtasks like a code block: they start and end inside the try.

// Java 25: javac --release 25 --enable-preview ; java --enable-preview   (API changed in JEP 505: open() + Joiner)
Dashboard load(long userId) throws InterruptedException {
    try (var scope = StructuredTaskScope.open()) {              // default: all must succeed
        Subtask<User> user          = scope.fork(() -> userClient.find(userId));      // each fork = new virtual thread
        Subtask<List<Order>> orders = scope.fork(() -> orderClient.recent(userId));
        scope.join();       // waits for both. If one fails: the other is cancelled and join() throws FailedException
        return new Dashboard(user.get(), orders.get());
    }                       // leaving the block guarantees no subtask is still running
}

// "First successful answer wins" (e.g. query 2 replicas, take the fastest)
try (var scope = StructuredTaskScope.open(StructuredTaskScope.Joiner.<Price>anySuccessfulResultOrThrow())) {
    scope.fork(() -> replicaA.price(sku));
    scope.fork(() -> replicaB.price(sku));
    return scope.join();    // the first result; the slower subtask is cancelled
}

@Async

@Configuration
@EnableAsync                                   // turns on the @Async proxy
class AsyncConfig {
    @Bean
    ThreadPoolTaskExecutor reportExecutor() {  // a dedicated, bounded pool for one kind of work
        var ex = new ThreadPoolTaskExecutor();
        ex.setCorePoolSize(4);
        ex.setMaxPoolSize(8);
        ex.setQueueCapacity(100);
        ex.setThreadNamePrefix("report-");
        ex.setTaskDecorator(new MdcTaskDecorator());   // copy MDC (traceId) to the worker thread
        ex.setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy());
        return ex;   // Spring calls initialize() and shutdown() for you
    }
}

@Service
class ReportService {
    @Async("reportExecutor")                    // runs on report-N, the caller returns immediately
    public CompletableFuture<Report> build(long id) {
        return CompletableFuture.completedFuture(heavyWork(id));
    }
    @Async                                     // void: exceptions go to AsyncUncaughtExceptionHandler (logged)
    public void sendEmail(String to) { ... }
}

class MdcTaskDecorator implements TaskDecorator {
    public Runnable decorate(Runnable task) {
        Map<String, String> mdc = MDC.getCopyOfContextMap();          // captured on the caller thread
        return () -> {
            if (mdc != null) MDC.setContextMap(mdc);
            try { task.run(); } finally { MDC.clear(); }              // runs on the worker thread
        };
    }
}

Remember the proxy rules: @Async does nothing on this.method() calls or on private methods, and the async method does not share the caller's transaction.

}
Scheduled jobs with several instances With 3 pods, every @Scheduled method runs 3 times. Use a distributed lock (ShedLock with a DB table, a Redis lock) or a single scheduler service. synchronized only protects inside one JVM.
