Q56–Q65: RabbitMQ & asynchronous communication

Brokers, AMQP, exchanges, reliability, dead letters and retries, ordering, duplicates, Kafka comparison, Spring AMQP, and a design for a client → sales → trader price-request flow.

Fundamentals

Q56.What is a message broker, and why use async messaging in a workflow like ASTRO's?

A message broker is a server that receives messages from producers, stores them safely, and delivers them to consumers. Producers and consumers don't know about each other, only about the broker. It is the producer-consumer pattern with the buffer moved out of your JVM into a durable, shared, networked service.

flowchart LR
  P1[Client-facing app] -->|publish| B{{Broker: RabbitMQ}}
  P2[Pricing engine] -->|publish| B
  B -->|deliver| C1[Sales desk service]
  B -->|deliver| C2[Trader desk service]
  B -->|deliver| C3[Audit / reporting]

Why async messaging in a multi-step business workflow (here: an internal system where a client's request goes through sales and traders, which I'll call "ASTRO" since the question does):

  • Decoupling in time: the trader desk service can be restarting or slow; requests wait in a queue instead of failing.
  • Human steps: a salesperson or trader may answer in seconds or minutes. Holding an HTTP connection (and a thread) open that long is wrong; a message + state machine is natural.
  • Load leveling: bursts of requests (market open, news) are buffered and consumed at a sustainable rate.
  • Fan-out: the same event (quote accepted) goes to booking, risk, audit and notifications without the sender knowing them.
  • Reliability: persistent messages + acknowledgements → no request is lost if a service crashes.
  • Auditability: every step is an explicit message that can be logged and replayed for compliance.
  • Scalability: add consumers to process more in parallel.

Costs: eventual consistency, duplicates, ordering, and a broker to operate and monitor. See Q65 for a concrete design.

Q57.Explain RabbitMQ's architecture.

RabbitMQ implements AMQP 0-9-1 (also AMQP 1.0, MQTT, STOMP, and its own Streams protocol). The key idea: producers never publish to a queue directly; they publish to an exchange, which routes copies to queues according to bindings.

  end

    X -->|binding: order.*| Q1[(Queue: billing.orders)]

    X -->|binding: #| Q3[(Queue: audit)]

  Q1 -->|push + ack| C1[Consumer: billing]
  Q2 -->|push + ack| C2[Consumer: email]
  Q3 -->|push + ack| C3[Consumer: audit]

Management UI (port 15672) shows queues, rates, unacked counts, consumers, and lets you publish/get messages for debugging.

Reliability

Q59.How do you make sure messages aren't lost in RabbitMQ?

A message can be lost at three points. Protect each one:

flowchart LR
  P[Producer] -- "1. publisher confirms
+ mandatory/returns" --> X{{Exchange}}
  X --> Q[("2. durable quorum queue
persistent messages")]
  Q -- "3. manual ack AFTER processing" --> C[Consumer]
  1. Producer → broker
    • Publisher confirms: the broker acks each message once it is safely stored (for quorum queues: replicated to a majority). No confirm / a nack → resend.
    • Mandatory flag + returns: if the exchange can't route the message to any queue, it is returned instead of silently dropped.
    • Publish from an outbox table so a crash between DB commit and publish doesn't lose the event (Q50).
  2. Inside the broker
    • Durable exchanges and queues (survive restart) and persistent messages (delivery_mode=2, Spring's default).
    • Quorum queues replicated across 3+ nodes (survive a node loss). Classic mirrored queues are removed in RabbitMQ 4.
    • Avoid overflowing: x-max-length with reject-publish rather than silently dropping, monitor queue depth and disk/memory alarms.
  3. Broker → consumer
    • Manual (or Spring AUTO) acknowledgement: ack only after the work is done (DB committed). If the consumer dies before acking, the broker redelivers.
    • Never use auto-ack (Spring's NONE) for important messages: the broker forgets the message as soon as it is sent.
    • Failed messages go to a dead letter queue instead of being dropped (Q60).
spring:
  rabbitmq:
    publisher-confirm-type: correlated   # enable publisher confirms
    publisher-returns: true
    template:
      mandatory: true
    listener:
      simple:
        acknowledge-mode: auto           # Spring acks after the listener returns normally, nacks on exception
        prefetch: 20

Result: at-least-once delivery. The flip side: duplicates are possible, so consumers must be idempotent (Q62).

Q60.What is a dead letter queue, and how do you handle retries?

A dead letter exchange (DLX) is where RabbitMQ re-publishes a message from a queue when it:

  • is rejected/nacked with requeue=false by a consumer,
  • expires (message TTL or queue x-message-ttl),
  • is dropped because the queue exceeded its max length,
  • exceeded the quorum queue delivery limit (x-delivery-limit; RabbitMQ 4 sets a default of 20).

The queue bound to that DLX is the dead letter queue (DLQ): a parking lot for messages that need a human or a later replay. The x-death header records why and how often.

Retry strategies

StrategyHowTrade-off
Immediate requeuenack with requeue=trueA "poison" message loops forever at full speed. Avoid.
In-memory retrySpring retry interceptor: retry 3× with backoff inside the listener, then reject → DLQSimple; blocks the consumer thread during backoff; retries lost if the app dies.
Delayed retry via TTL queueOn failure publish to orders.retry.10s (TTL 10 s, DLX = main exchange) → message comes back after 10 s. Several tiers: 10 s, 1 min, 10 min.Non-blocking, survives restarts; more topology.
Delayed-message pluginpublish with x-delay headerSimple; plugin needed.
flowchart LR
  X{{orders exchange}} --> Q[(orders.queue)]
  Q --> C[Consumer]
  C -- "fails: transient, attempt < 3" --> RX{{retry exchange}} --> RQ[("orders.retry
TTL 30s, DLX = orders exchange")]
  RQ -- "after 30 s, dead-lettered back" --> X
  C -- "fails: permanent or attempt = 3" --> DLX{{orders.dlx}} --> DLQ[(orders.dlq: alert + manual replay)]

@Configuration
class RabbitTopology {
    @Bean Queue orders() {
        return QueueBuilder.durable("orders.queue")
                .quorum()
                .deadLetterExchange("orders.dlx")          // rejected messages go here
                .deadLetterRoutingKey("orders.dlq")
                .build();
    }
    @Bean DirectExchange dlx() { return new DirectExchange("orders.dlx"); }
    @Bean Queue dlq() { return QueueBuilder.durable("orders.dlq").quorum().build(); }
    @Bean Binding dlqBinding() { return BindingBuilder.bind(dlq()).to(dlx()).with("orders.dlq"); }
}
spring.rabbitmq.listener.simple:
  default-requeue-rejected: false     # an exception rejects WITHOUT requeue → goes to the DLX
  retry:
    enabled: true                     # stateless in-memory retry before rejecting
    max-attempts: 3
    initial-interval: 1s
    multiplier: 2

Distinguish transient errors (DB timeout: retry) from permanent ones (invalid JSON, business rule: no retry, straight to DLQ; throw AmqpRejectAndDontRequeueException). Monitor and alert on DLQ depth.

Q61.How do you handle message ordering and scaling consumers?

A single queue is FIFO, and with one consumer messages are processed in order. As soon as you add consumers (competing consumers) or prefetch > 1 with concurrency, ordering across the queue is lost: message 2 may finish before message 1. Redeliveries after a failure also break order.

flowchart LR
  subgraph S1["Scale out: no global order"]
    Q[(queue: m1 m2 m3 m4)] --> C1[consumer 1: m1, m3]
    Q --> C2[consumer 2: m2, m4]
  end

Usually you don't need global order, only order per entity (per order id, per client). Options:

  1. Partition by key: N queues, route each entity always to the same queue (consistent-hash exchange plugin, or compute hash(orderId) % N as the routing key), one consumer per queue. Order per key, parallelism N.
  2. Single active consumer (x-single-active-consumer): many consumers registered for failover, only one receives at a time; prefetch 1 for strict order.
  3. Make order irrelevant: include a version/sequence number or timestamp and let the consumer ignore stale updates (update ... where version < :newVersion). Often the most robust choice.
  4. RabbitMQ Streams / super streams (partitioned streams), or Kafka, which orders within a partition by design.
flowchart LR
  P[producer] --> H{{"consistent-hash exchange
key = clientId"}}
  H --> Q1[(rfq.0)] --> C1[consumer A]
  H --> Q2[(rfq.1)] --> C2[consumer B]
  H --> Q3[(rfq.2)] --> C3[consumer C]

Scaling consumers

  • More consumer threads per instance: @RabbitListener(concurrency = "4-10") or spring.rabbitmq.listener.simple.concurrency/max-concurrency.
  • More instances (pods): all consume the same queue, the broker round-robins among consumers.
  • Prefetch (default 250 in Spring AMQP): how many unacked messages each consumer may hold. High = throughput; low (1–10) = fairer distribution of slow tasks and less work stuck on a dying consumer.
  • Scale on queue depth (KEDA) rather than CPU.
  • Downstream limits: 50 consumers × DB calls may overload the DB.
Q62.How do you deal with duplicate messages?

With at-least-once delivery, duplicates happen: producer resends after a missing confirm, consumer crashes after doing the work but before acking, network hiccups. "Exactly once" end-to-end isn't something the broker can give you; you get effectively once by making consumers idempotent: processing the same message twice has the same effect as once.

sequenceDiagram
  participant Q as Queue
  participant C as Consumer
  participant DB as DB
  Q->>C: msg id=abc (1st delivery)
  C->>DB: BEGIN, INSERT processed_messages(abc), do work, COMMIT
  C--xQ: crash before ack
  Q->>C: msg id=abc (redelivered)
  C->>DB: INSERT processed_messages(abc) → unique violation
  C->>Q: ack (already done, skip)
  1. Deduplication table: store the message_id in a table with a unique constraint, in the same transaction as the business change. If the insert fails → already processed → just ack.
  2. Naturally idempotent operations: "set status = BOOKED where id = 42" (not "increment"), upserts (MERGE / INSERT … ON CONFLICT DO NOTHING), unique business keys (one quote per RFQ id).
  3. Version checks: apply only if event.version > current.version.
  4. Idempotency key in a fast store (Redis SET key NX EX 86400) for non-DB side effects, accepting the small window it leaves.
@RabbitListener(queues = "billing.orders")
@Transactional
public void on(OrderPlaced e, @Header(AmqpHeaders.MESSAGE_ID) String messageId) {
    int inserted = jdbc.update("insert into processed_message(id) values (?) on conflict do nothing", messageId);
    if (inserted == 0) return;                // duplicate → ack and skip
    invoiceService.createFor(e.orderId());    // same transaction as the dedup row
}

Producers should set a stable message_id (e.g. the outbox row id), not a random one per send attempt.

Q63.RabbitMQ vs Kafka?

RabbitMQ: smart broker, message queue

Routes messages through exchanges to queues; a message is deleted once acked. Push delivery to consumers, per-message acks, flexible routing, priorities, TTL, DLX, request/reply. Great for commands, work queues, task distribution, RPC-style workflows.

Kafka: distributed commit log

Producers append to partitioned topics; messages are retained (days, or forever with compaction) regardless of consumption. Consumers pull and track their own offset; many consumer groups read the same data independently and can replay. Great for event streaming, high throughput, event sourcing, analytics pipelines.

RabbitMQKafka
Modelqueue (consumed = gone)log (retained, replayable)
Deliverypush, prefetchpull, batches
Orderingper queue with one consumerper partition (by key)
Scaling consumersadd consumers freely (competing)max parallelism = number of partitions per group
Routingrich (direct, topic, fanout, headers)by topic + partition key only
Throughputtens of thousands msg/s per queuemillions msg/s per cluster
Per-message featuresTTL, priority, DLX, delaysnone built-in (DLQ is an app pattern)
Replay old messagesno (except Streams)yes, reset offsets
SpringSpring AMQP (@RabbitListener)Spring for Apache Kafka (@KafkaListener)

Rule of thumb: "do this task" → RabbitMQ; "this happened, anyone may care, maybe later" at high volume → Kafka. RabbitMQ Streams narrow the gap for replayable logs.

Spring & design

Q64.How do you use RabbitMQ with Spring?

Add spring-boot-starter-amqp (Spring AMQP). Boot auto-configures a ConnectionFactory (caching channels), a RabbitTemplate for sending, a RabbitAdmin that declares your queues/exchanges/bindings beans on the broker at startup, and listener containers for @RabbitListener.

spring:
  rabbitmq:
    host: rabbit.internal
    port: 5672
    username: orders
    password: ${RABBIT_PASSWORD}
    virtual-host: /shop
    listener:
      simple:
        concurrency: 2
        max-concurrency: 8
        prefetch: 20
@Configuration
class RabbitConfig {
    @Bean TopicExchange ordersExchange() { return new TopicExchange("orders"); }
    @Bean Queue billingQueue() { return QueueBuilder.durable("billing.orders").quorum().deadLetterExchange("orders.dlx").build(); }
    @Bean Binding billingBinding() { return BindingBuilder.bind(billingQueue()).to(ordersExchange()).with("order.*"); }

    @Bean MessageConverter json() { return new Jackson2JsonMessageConverter(); }   // JSON instead of Java serialization
    // (Spring AMQP 4 / Boot 4 with Jackson 3: JacksonJsonMessageConverter)
}

public record OrderPlaced(long orderId, BigDecimal amount) {}

@Service
class OrderPublisher {
    private final RabbitTemplate rabbit;
    OrderPublisher(RabbitTemplate rabbit) { this.rabbit = rabbit; }

    void publish(OrderPlaced e) {
        rabbit.convertAndSend("orders", "order.placed", e, m -> {
            m.getMessageProperties().setMessageId("order-" + e.orderId());   // stable id for dedup
            return m;
        });
    }
}

@Component
class BillingListener {
    @RabbitListener(queues = "billing.orders")
    void handle(OrderPlaced event) {             // JSON → record by the MessageConverter
        billing.invoice(event);                  // returns normally → ack; throws → nack (→ DLQ if not requeued)
    }
}
  • Request/reply: rabbit.convertSendAndReceive(...) + a listener returning a value (uses reply_to and correlation_id); set a reply timeout.
  • Testing: Testcontainers RabbitMQContainer with @ServiceConnection; @RabbitListenerTest for spying listeners.
  • Tracing: Boot can propagate trace headers through RabbitTemplate and listeners (enable observation: spring.rabbitmq.template.observation-enabled, spring.rabbitmq.listener.simple.observation-enabled).
  • With spring.threads.virtual.enabled=true, listener containers use virtual threads.
Q65.How would you design the messaging for a client → sales → trader price request flow?

This is an RFQ (Request For Quote) workflow: a client asks for a price, a salesperson enriches/approves it, a trader prices it, the quote goes back through sales to the client, who can accept within a short validity window. Design goals: no lost requests, clear state, timeouts (prices go stale fast), auditability, per-request ordering, and the ability to route to the right desk.

1. Model the RFQ as a state machine, persisted by an RFQ service

stateDiagram-v2
  [*] --> REQUESTED: client submits
  REQUESTED --> WITH_SALES: routed to sales desk
  WITH_SALES --> WITH_TRADER: sales forwards (adds client tier / margin)
  WITH_SALES --> REJECTED: sales declines
  WITH_TRADER --> QUOTED: trader prices
  WITH_TRADER --> REJECTED: trader declines
  QUOTED --> ACCEPTED: client accepts before expiry
  QUOTED --> EXPIRED: validity (e.g. 15 s) passes
  REQUESTED --> EXPIRED: no answer in time
  WITH_SALES --> EXPIRED
  WITH_TRADER --> EXPIRED
  ACCEPTED --> BOOKED: trade booked

2. Topology

flowchart LR
  CL[Client portal / API] -->|"rfq.requested.{assetClass}.{ccy}"| X{{topic exchange: rfq}}
  X -->|"rfq.requested.#"| QS[(sales.desk.requests
quorum)]
  QS --> SALES[Sales service + sales UI]
  SALES -->|"rfq.forwarded.fx.eur"| X
  X -->|"rfq.forwarded.fx.*"| QT[(trader.fx.requests)]
  X -->|"rfq.forwarded.rates.*"| QR[(trader.rates.requests)]
  QT --> TR[Trader service + trader UI / pricing engine]
  TR -->|"rfq.quoted.fx.eur"| X
  X -->|"rfq.quoted.#"| QQ[(sales.quotes)] --> SALES
  SALES -->|"rfq.quote-published"| X
  X -->|"rfq.quote-published"| QC[(client.notifications)] --> CL
  X -->|"#"| QA[(audit: every event)]
  QS -. failures .-> DLX{{rfq.dlx}} --> DLQ[(rfq.dlq)]
  • Topic exchange with routing keys rfq.{event}.{assetClass}.{currency} so desks bind only to what they handle (FX vs rates, EUR desk vs USD desk) and audit binds #.
  • Quorum queues, persistent messages, publisher confirms, manual acks (Q59), DLX per queue (Q60).
  • Every message carries rfqId as correlation_id, a unique message_id, a version/sequence, the validUntil timestamp, and the traceparent header.

3. Timeouts and staleness

  • Set a per-message TTL (expiration) equal to the remaining validity: an RFQ nobody picked up in time expires and dead-letters to an rfq.expired handler that marks it EXPIRED and notifies the client.
  • Consumers also check validUntil before acting (TTL is only checked at the head of the queue).
  • Quotes carry their own expiry; acceptance after expiry is rejected by the RFQ service (the source of truth), not by the broker.

4. Correctness

  • Idempotent handlers: transitions are conditional updates (update rfq set state='QUOTED' where id=? and state='WITH_TRADER'); a duplicate or late message changes nothing (Q62).
  • Ordering per RFQ is guaranteed by the state machine + versions, so many consumers can work in parallel (Q61). If a desk needs strict per-client order, partition by clientId.
  • Outbox: each service writes its state change and the outgoing event in one DB transaction (Q50).
  • Real-time UIs: sales/trader screens get updates over WebSocket/SSE from their service, which consumes the queues; the human click goes back as an HTTP command that produces the next event.
  • Auditability: the audit queue persists every event (and/or a RabbitMQ Stream for replay) for compliance (who quoted what, when).
  • Observability: one trace per RFQ across all hops, dashboards on queue depth and time-in-state, alerts on DLQ messages and expiry rate.
