2. Reactive Spring Boot with WebFlux (Java 21)

How multithreading works in a reactive app, what Netty does, what Mono/Flux really are, and how reactive Spring Boot differs from "normal" Spring MVC.

The problem WebFlux solves

In Spring MVC each request owns one platform thread from start to finish, including while it waits on the database or another service. A typical request is 5 % CPU and 95 % waiting.

WebFlux gets high concurrency with very few threads by never blocking. The price: your code becomes a pipeline of operators (Mono/Flux) and every library in the path (DB driver, HTTP client) must be non-blocking too.

What Netty does

Netty is a Java networking library: it manages sockets, reads and writes bytes with non-blocking I/O, and decodes protocols (HTTP/1.1, HTTP/2, WebSocket). WebFlux uses it through Reactor Netty, a thin reactive wrapper. Spring Boot's spring-boot-starter-webflux starts a Reactor Netty server by default (Tomcat or Jetty are possible too, using Servlet non-blocking I/O).

The key Netty concepts

ConceptWhat it is
ChannelOne open connection (socket).
EventLoopOne thread running an endless loop: ask the OS selector "which of my channels have data / can be written?" (epoll on Linux, kqueue on macOS, NIO selector otherwise), handle those events, run queued tasks, repeat.
EventLoopGroupA set of event loops. Each channel is assigned to one event loop for its whole life, so its handlers are never called by two threads at once (no locks needed).
ChannelPipeline / ChannelHandlerA chain of handlers each connection's bytes flow through: TLS decryption, HTTP decoding, your application.
ByteBufNetty's pooled, reference-counted byte buffer (WebFlux wraps it as DataBuffer).

Reactor Netty creates by default max(CPU cores, 4) event loop threads (property reactor.netty.ioWorkerCount), named reactor-http-nio-N (or reactor-http-epoll-N with the native transport). All your controller code runs on these few threads, which is why blocking them is catastrophic.

Reactive Streams: the contract

Reactor implements the Reactive Streams specification (4 interfaces; copied into the JDK as java.util.concurrent.Flow in Java 9):

interface Publisher<T>  { void subscribe(Subscriber<? super T> s); }
interface Subscriber<T> { void onSubscribe(Subscription s); void onNext(T t); void onError(Throwable t); void onComplete(); }
interface Subscription  { void request(long n); void cancel(); }
interface Processor<T, R> extends Subscriber<T>, Publisher<R> {}
sequenceDiagram
  participant S as Subscriber (e.g. WebFlux writing the HTTP response)

  S->>P: subscribe(subscriber)
  P->>S: onSubscribe(subscription)
  S->>P: request(32)   (backpressure: I can take 32)
  P->>S: onNext(row 1) ... onNext(row 32)
  S->>P: request(32)
  P->>S: onNext(row 33) ... 
  P->>S: onComplete()   (or onError(e), both are terminal)

The important new idea is request(n): the consumer controls the speed. That is backpressure (more in Q36).

Mono and Flux

Mono<T>: 0 or 1 value

Like an async Optional / CompletableFuture. Find by id, save, one HTTP call.

Flux<T>: 0 to N values

Like an async Stream, possibly infinite. Query results, server-sent events, Kafka/RabbitMQ streams.

Flux<Integer> numbers = Flux.just(1, 2, 3, 4)
    .filter(n -> n % 2 == 0)          // 2, 4
    .map(n -> n * 10)                 // 20, 40
    .doOnNext(n -> log.info("got {}", n));
// NOTHING has happened yet: this is only a recipe ("assembly time").

numbers.subscribe(n -> System.out.println(n));   // now it runs ("subscription time")
// In WebFlux you never call subscribe() yourself: you return the Mono/Flux and the framework subscribes.

One WebFlux request, step by step

@RestController
@RequestMapping("/orders")
class OrderController {
    private final OrderRepository orders;   // ReactiveCrudRepository (R2DBC)
    private final WebClient pricing;        // non-blocking HTTP client

    OrderController(OrderRepository orders, WebClient pricingWebClient) {   // a WebClient @Bean built in a @Configuration
        this.orders = orders;
        this.pricing = pricingWebClient;
    }

    @GetMapping("/{id}")
    Mono<OrderView> get(@PathVariable long id) {
        return orders.findById(id)                                   // Mono<Order>: query sent, thread released
            .switchIfEmpty(Mono.error(new ResponseStatusException(HttpStatus.NOT_FOUND)))
            .flatMap(order -> pricing.get().uri("/price/{sku}", order.sku())
                .retrieve().bodyToMono(Price.class)                   // HTTP call, thread released again
                .map(price -> new OrderView(order, price)))
            .timeout(Duration.ofSeconds(2));
    }

    @GetMapping(value = "/stream", produces = MediaType.TEXT_EVENT_STREAM_VALUE)
    Flux<Order> stream() { return orders.findAll().delayElements(Duration.ofMillis(100)); }   // server-sent events
}

interface OrderRepository extends ReactiveCrudRepository<Order, Long> {
    Flux<Order> findByCustomerId(long customerId);
}

The request "jumps" between whatever event loop thread delivers each event; no thread is ever parked waiting for it. That is why ThreadLocal-based things (MDC, SecurityContextHolder, @Transactional with JDBC) do not work as usual in WebFlux; see context.

Threading in Reactor: Schedulers, publishOn, subscribeOn

By default Reactor is concurrency-agnostic: operators run on whatever thread delivered the signal (the event loop, in WebFlux). You change threads explicitly with Schedulers:

SchedulerThreadsFor
Schedulers.immediate()the current threadno switch
Schedulers.single()one reusable threadlow-volume sequential tasks
Schedulers.parallel()one per CPU core (parallel-N)CPU-bound, non-blocking work
Schedulers.boundedElastic()grows up to 10 × cores, queue up to 100 000 tasks, idle threads removed after 60 s (boundedElastic-N)wrapping blocking calls (legacy JDBC, file I/O, blocking SDKs). On Java 21+ it can use virtual threads (-Dreactor.schedulers.defaultBoundedElasticOnVirtualThreads=true, Reactor 3.6+).
Schedulers.fromExecutorService(ex)yourscustom pools

publishOn(scheduler)

Everything after it (downstream) runs on that scheduler. Position matters; you can use it several times.

subscribeOn(scheduler)

Changes the thread on which the subscription and therefore the source start emitting. Position in the chain does not matter; if there are several, the one closest to the source wins.

Flux.range(1, 3)
    .doOnNext(i -> log("A", i))                 // runs on: boundedElastic-1 (because of subscribeOn)
    .publishOn(Schedulers.parallel())
    .map(i -> { log("B", i); return i * 2; })   // runs on: parallel-1
    .subscribeOn(Schedulers.boundedElastic())
    .subscribe(i -> log("C", i));               // runs on: parallel-1

Blocking inside a reactive chain

// WRONG: blocks the event loop thread for the whole JDBC query
@GetMapping("/{id}")
Mono<Customer> get(@PathVariable long id) {
    Customer c = jdbcTemplate.queryForObject("select ...", mapper, id);   // blocking!
    return Mono.just(c);
}

// WRONG: .block() on an event loop → IllegalStateException
// "block()/blockFirst()/blockLast() are blocking, which is not supported in thread reactor-http-nio-2"
Price p = pricingClient.get().retrieve().bodyToMono(Price.class).block();

// RIGHT (when you must call blocking code): move it to boundedElastic
@GetMapping("/{id}")
Mono<Customer> get(@PathVariable long id) {
    return Mono.fromCallable(() -> jdbcTemplate.queryForObject("select ...", mapper, id))  // lazy
               .subscribeOn(Schedulers.boundedElastic());                                // runs off the event loop
}

Detect accidental blocking in tests with BlockHound (BlockHound.install()): it throws when a blocking JDK call happens on a non-blocking thread.

Backpressure strategies

fastSensorFlux
    .onBackpressureBuffer(10_000,                         // buffer up to 10k, then…
        dropped -> log.warn("dropped {}", dropped),
        BufferOverflowStrategy.DROP_OLDEST)
    .limitRate(100)                                       // request 100 at a time from upstream (refill at 75 %)
    .concatMap(this::saveToDb, 1);

hotPrices.onBackpressureLatest();   // slow consumer only cares about the newest price
hotClicks.onBackpressureDrop();     // drop what can't be handled

Over HTTP, backpressure ends at the TCP layer: if the client reads slowly, Netty's write buffer fills, the channel becomes not-writable and Reactor Netty stops requesting more from your Flux.

Context instead of ThreadLocal

Because a request hops between threads, Reactor carries request-scoped data in its own Context attached to the subscription:

Mono<String> greet() {
    return Mono.deferContextual(ctx -> Mono.just("Hello " + ctx.get("user")));
}
greet().contextWrite(Context.of("user", "alex"));          // written downstream, read upstream

// Spring Security in WebFlux:
ReactiveSecurityContextHolder.getContext().map(sc -> sc.getAuthentication().getName());

For logs and tracing, Spring Boot 3.2+ can copy Context ↔ ThreadLocal (MDC, Micrometer tracing) automatically: spring.reactor.context-propagation=auto (it calls Hooks.enableAutomaticContextPropagation()).

Transactions in WebFlux @Transactional works with R2DBC via R2dbcTransactionManager (it stores the transaction in the Reactor Context, not a ThreadLocal). It does not work if you wrap blocking JPA in boundedElastic and expect one transaction across several such calls.

Errors and testing

Mono<Price> price = webClient.get().uri("/price/{sku}", sku).retrieve()
    .onStatus(HttpStatusCode::is4xxClientError, r -> Mono.error(new UnknownSkuException(sku)))
    .bodyToMono(Price.class)
    .timeout(Duration.ofMillis(800))
    .retryWhen(Retry.backoff(3, Duration.ofMillis(100)).filter(e -> !(e instanceof UnknownSkuException))
        .onRetryExhaustedThrow((spec, signal) -> signal.failure()))   // rethrow the last error, not RetryExhaustedException
    .onErrorResume(TimeoutException.class, e -> cache.lastKnown(sku));   // fallback

// Unit test with StepVerifier (reactor-test)
StepVerifier.create(Flux.just(1, 2, 3).map(i -> i * 2))
    .expectNext(2, 4, 6)
    .verifyComplete();

// Web layer test
@WebFluxTest(OrderController.class)
class OrderControllerTest {
    @Autowired WebTestClient client;
    @MockitoBean OrderRepository orders;
    @MockitoBean WebClient pricingWebClient;               // the slice only loads web beans, so mock the collaborators

What about virtual threads?

Since Java 21, Spring MVC + spring.threads.virtual.enabled=true gives most of the scalability benefit of WebFlux (thousands of concurrent waiting requests) while keeping simple blocking code, JPA and ThreadLocals. WebFlux still wins for streaming, backpressure, and declarative composition of many async calls (e.g. Spring Cloud Gateway).

flowchart TD
  A{Need streaming / backpressure / SSE / WebSocket at scale, or a gateway?} -- yes --> W[WebFlux]
  A -- no --> B{Is the whole stack non-blocking already
R2DBC, WebClient, reactive drivers?}
  B -- yes, team knows Reactor --> W
  B -- no --> C{Many concurrent requests that mostly wait on I/O?}
  C -- yes --> V[Spring MVC + virtual threads, Java 21+]
  C -- no --> M[Spring MVC, platform threads]

You cannot mix them in one app's web layer: if both starters are on the classpath, Boot picks Spring MVC. You can, however, use WebClient inside an MVC app.
